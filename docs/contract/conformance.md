# Conformance cases

These are the acceptance tests for the contract. Each case states the observable behavior. They assert behavior, not storage internals. The storage-level mutant sweep of the overlap predicate is a separate test, not listed here.

A case is satisfied when a conforming engine produces the stated result. The ids are stable and referenced by the requirements.

## C1. One transaction

Two concurrent creates for the same venue, date, time, and table produce exactly one booking and one `slot_taken`. The loser never double-books the table.

## C2. Idempotent create

Replaying a create with the same idempotency key returns the original reservation id and version. No second reservation exists.

## C3. Snapshot is not a hold

Availability returns a free slot. A create for that slot then either fails with `slot_taken` or assigns a different eligible table. It never double-books, and a failed create writes nothing. A create with explicit tables that are no longer free fails with `slot_taken`.

## C4. Modify bumps the version

A modify that changes a field produces a version one greater than before. A no-op modify produces no new version. The confirmation is sent once for the new version when the modify carries `partySize` or `tables`. A modify with only consent, rating, the booking note, or reconfirmation sends no email.

A modify that changes only consent, rating, or the booking note is allowed on `booked`, `seated` and `attended`. A change to party size or tables is allowed only on `booked` and `seated`, and fails with `invalid_transition` otherwise. A change to reconfirmation is allowed only on `booked`. `cancelled` and `no_show` reject every modify.

## C5. Erasure

Erasure by guest id returns the counts of erased reservations, guest records, and waitlist entries, and no personal value remains for that guest. The guest id is the record id read from `guest.guestId`. Erasure deletes the guest record and any guest merged into it, and `erasedGuests` reports how many. Each erased reservation keeps its date, party size, and status, with no guest linked. It deletes the venue's waitlist entries whose contact normalizes to the guest's keys and leaves other venues and other guests untouched. A guest id from another venue erases nothing. A guest id that is not a record is read as a contact, a deprecated fallback, and a contact that matches no record reports `erasedGuests` 0. Erasure by principal blanks the reservations that principal owns, then deletes every guest record of the venue that was linked to them and has no remaining reservation that is not erased, with the guests merged into it. A guest with a visit owned by another principal stays, and `erasedGuests` counts the records deleted. Each tombstone it emits carries a hash of the reservation id, visible in the event feed.

## C6. Notice address

Enabling a venue without a notice address via `venue.setConfig` fails with `notice_address_required`. Clearing the address while the venue is enabled fails. A venue already enabled without one stays enabled.

## C7. Party size

A party above the venue maximum fails with `party_size_too_large`. A party that fits no table combination fails with `no_suitable_table`.

## C8. Hours

A time outside the hours, off the slot grid, or after the last seating fails with `outside_hours`. A time within the lead time fails with `lead_time_violation`.

## C9. Status transitions

`reservation.status` moves a reservation to seated, attended, or no_show and emits an event. A transition that is not allowed fails with `invalid_transition`. Cancelling twice returns `already_cancelled` on the second call.

## C10. Venue isolation

A request scoped to one venue never returns data from another venue. A request for a venue the caller cannot see returns `venue_not_found`, the same as an unknown venue.

## C11. Event feed

A consumer that polls the feed from a cursor sees events with stable, monotonic ids and no gap. Replaying from an earlier cursor re-emits the same ids, which the consumer deduplicates.

## C12. Attribution

The engine sets `basis`, `owner_principal`, and `booked_via` from the authenticated channel. A write that tries to set them is ignored, and the stored value comes only from the channel.

## C13. Cursor expiry

Polling the event feed with a cursor older than the venue's retention period fails with `expired_cursor`. A cursor within the retention period returns no gap in the event ids.

## C14. Consent

A reservation carries `guest.consent`, one of `unknown`, `granted`, or `denied`. A create or walk-in without it returns `unknown` and no `consentRecordedAt`. A value outside the three fails with `invalid_request`. A modify that changes consent bumps the version by one and emits one `modified` event. A modify that sets the same value changes nothing. Consent changing to `granted` or `denied` sets `consentRecordedAt`. Reads through get, list, search, and agenda return the stored value. Erasure resets consent to `unknown` and clears `consentRecordedAt`, and its counts still report reservations and guests erased.

## C15. Webhooks

Registering an https endpoint returns `201` with its id and a secret, and the secret never appears in a listing. A new endpoint receives only events written after registration. Each event arrives as a POST whose `OpenCovers-Signature` verifies with HMAC-SHA256 of `<t>.<raw body>` under the secret and fails under any other key. Events reach an endpoint in id order. A failed delivery stops that endpoint, retries the same event after `min(30s × 2^(failures − 1), 1h)`, and on success resumes without skipping or repeating acknowledged events. A failing or slow endpoint does not delay another. Two workers running at once deliver each event to an endpoint exactly once. A cursor behind the retention watermark jumps to it and records the drop in `lastError`. A URL that is not https, carries credentials, or resolves to a loopback, private, link-local, CGNAT, unspecified, or multicast address, in IPv4, IPv6, or IPv4-mapped form, fails with `webhook_url_rejected`. A host that resolves to such an address at delivery time is not contacted. A venue holds at most 5 endpoints, and a webhook id from another venue returns `webhook_not_found`.

## C16. Rating

A reservation carries `rating`, an integer from 1 to 5 or null, and `ratingRecordedAt`, a timestamp or null. A create or walk-in without it returns both as null. A value outside 1 to 5, a non-integer, or a string fails with `invalid_request`. A modify that changes the rating bumps the version by one and emits one `modified` event. A modify that sets the same value changes nothing. Setting null clears the rating and `ratingRecordedAt`. A key without `write` cannot set it. Reads through get, list, search, and agenda return the stored value. Erasure resets both to null.

## C17. Guest identity

A create, walk-in, or seated waitlist entry with a contact returns `guest.guestId`. Two bookings in one venue whose contacts normalize to the same key return the same `guestId`. An email that differs only in case or surrounding whitespace is the same key. Dots and `+` tags are different keys. A phone without a country code is read with the venue's `phoneCountry`, or the country of its time zone when that is null, so `600 123 456` and `+34 600 123 456` match in Spain. The name never matches. The same contact in two venues returns two different ids. A booking without a contact, or with a contact that does not normalize, succeeds and returns no `guestId`. Concurrent bookings for one new contact produce exactly one guest. Consent and rating stay on each reservation. A `phoneCountry` that is not a supported upper-case ISO 3166 alpha-2 code fails with `invalid_request`.

## C18. Guest retention

A guest whose latest visit is older than the venue's retention period, with no visit ending inside that period and no future booking, expires on the next retention run. Its record keeps its id and holds no email, phone, or name. Each reservation linked to it is blanked and unlinked as erasure does, keeps its date, party size, and status, and emits one `erased` event whose tombstone hash is the hash of the reservation id. A guest merged into it expires with it. A reservation with no guest record that holds a name, a contact, or a booking note and ended before the period is blanked the same way, with one `erased` event, and one that ends inside the period, ends in the future, or is booked or seated and not yet over stays. Waitlist entries older than the period are deleted. A guest inside the period stays, each venue uses its own period, and other venues are untouched. A reservation linked to a guest is left to guest expiry. A second run changes nothing, and two runs at once expire each guest once.

## C19. Guest merge

A key or session that can read the venue lists its guests by latest visit, then id, and pages through them with a cursor without gaps or repeats. It filters by a normalized contact or a name prefix. A guest merged into another or cleared by retention is not listed, and reading it fails with `guest_not_found`, as does a guest id of another venue. Reading a guest returns its visit count, first and latest visit, and the ids and statuses of the reservations it holds. Only an admin merges and unmerges, and a `read` or `write` key fails with `forbidden`. Merging B into A moves every reservation of B to A in one transaction, sets A's latest visit to the later of the two, and keeps B merged into A. Repeating the Idempotency-Key applies the merge once. Merging a guest into itself fails with `invalid_request`, a guest of another venue or a cleared guest fails with `guest_not_found`, and a source or target already merged fails with `guest_merged`, so A into B after B into A is rejected. A later booking with B's contact links to A. Unmerging B returns exactly the reservations moved at merge time, leaves later ones with A, and recomputes A's latest visit. A second unmerge and an unmerge of a guest never merged fail with `guest_not_merged`. Erasure by guest id, erasure by principal, and retention leave no personal value of the guests involved in the guest audit, and the merge can no longer be undone.

## C20. Availability explanation

A key or session that can read the venue asks why a date, time, and party size, with an optional zone, is or is not bookable. The answer has `available` and a list of reasons, empty when the time is bookable. Each reason has a `code` from the error vocabulary, a `message`, and `details`. A time outside every service returns `outside_hours` with the service hours. A time off the slot grid returns `outside_hours` with the interval and the grid times before and after it. A time after the last seating returns `outside_hours` with the last seating time. A time within the lead time returns `lead_time_violation` with the lead time and the earliest bookable date and time. A party above the capacity of the venue, or of the zone, returns `party_size_too_large` with the largest party. A party that the free tables cannot seat returns `no_suitable_table` with the counts of free and total tables, the free seats, and the largest free table. Several reasons come in that order, and a create for the same request fails with the code of the first. `available` is true exactly when a create would succeed and availability lists the time as free. A blocked time returns up to 3 nearest available times that day, nearest first, each of them bookable. The answer never contains a guest name, contact, reservation id, or table id. An unknown venue, or one the caller cannot see, returns `venue_not_found`.

## C21. Turn time and party limits

A venue sets `turnTimes` in its config, rows of `upTo` and `minutes` with `upTo` strictly increasing, at most 10 rows, and minutes from 15 to 480. A booking holds its tables for the minutes of the first row whose `upTo` is at least the party size, or of the last row for a larger party. With no rows it holds them for 120 minutes, and an empty array clears the rows. A walk-in uses the same turn time. With rows of 2 for 90, 4 for 120, and 8 for 150, a party of 2 booked at 20:00 frees its table at 21:30, a party of 4 at 22:00, and a party of 8 or more at 22:30. The requested booking is sized by its own party, so with a party of 2 at 22:00 a party of 2 fits at 20:30 and a party of 8 does not fit at 20:00. A service sets `minPartySize` and `maxPartySize`, integers of at least 1. A create below the minimum fails with `party_size_too_small`, above the maximum with `party_size_too_large`, and availability shows the time as unavailable. The explanation returns the reason with rule `service_limit`, the service, the party size, and the limit, after `lead_time_violation` and before the capacity and table reasons. A walk-in is not held to the limits. Null clears a limit, and a limit left out of an update keeps its value. A minimum above the maximum, a limit that is not an integer of at least 1, and malformed turn times fail with `invalid_request` and change nothing. A service without limits and a venue without turn times behave as before. Availability, create, and the explanation agree for every time and party size. Settings stay in their venue, and a `read` key cannot change them.

## C22. Role boundaries

Every venue route accepts a key or a staff session with a role for that venue, `read`, `write`, or `admin`. A `read` role cannot write anything. A `write` role creates, walks in, modifies, cancels, and moves reservations, including consent and rating, adds, seats, and cancels waitlist entries, manages webhooks, and erases. Changing the venue config, creating, updating, or deleting a service, a table, a floor item, or its layout, minting, listing, or revoking API keys, and merging or unmerging guests need `admin`. A `read` or `write` key or session that tries one fails with `forbidden`, and the config, services, tables, floor items, and keys read back unchanged. A session follows the same rule by its venue role.

## C23. Booking note

A reservation carries `commentary`, a string of at most 500 characters after trimming, empty when no note was given. A create or walk-in without it returns an empty string. A value that is not a string, or longer than 500 characters, fails with `invalid_request`. A modify that changes the note bumps the version by one and emits one `modified` event, sends no email, and may set it on an attended reservation. A modify that sets the same value changes nothing, and an empty string clears it. A key without `write` cannot set it. A modify on an erased reservation fails with `invalid_request`. Reads through get, list, search, and agenda return the stored value. Erasure and retention reset it to an empty string. The note is free text for staff and never holds health data, and the contract says so.

## C24. Overbooking ceiling

A venue has `overbookingCeiling` in its config, an integer from 0 to 1000, default 0. Any other value fails with `invalid_request`, changes nothing, and only an `admin` key sets it. At 0 a create that finds no free table combination fails with `no_suitable_table`, and a modify that would leave a booking without tables fails with it too. Above 0 a create that fits the venue but finds no free table combination is accepted when the party sizes of every `booked` or `seated` booking without tables whose window overlaps the new one, plus the new party, are at most the ceiling. The booking has `tables: []`, version 1, status `booked`, and holds no row in the table allocations. The next create that would pass the ceiling fails with `no_suitable_table`. A booking that is cancelled, attended, or a no-show stops counting. A booking that does not overlap does not count. The ceiling never admits a party larger than the venue, which keeps `party_size_too_large`, a create that names tables another booking holds, which keeps `slot_taken`, or a walk-in, which keeps `no_suitable_table`. Availability and the explanation show a time as bookable exactly when a create would succeed. Staff give the booking tables with a modify, and the database exclusion constraint still refuses a table that another booking holds, with `slot_taken`. A modify that raises the party of a booking without tables, or releases its tables, passes the same ceiling check. Concurrent creates never take more than the ceiling in total. A ceiling in one venue does not change another venue.

## C25. Reconfirmation

A reservation carries `reconfirmation`, one of `none`, `requested`, `confirmed`, `declined`, or `no_answer`, and `reconfirmationRecordedAt`, a timestamp or null. A create without it returns `none` and null. A create with a value returns it with a recorded time, and `none` records no time. Any other value, or a value that is not a string, fails with `invalid_request`, and so does a walk-in that carries the field. A modify that changes the value bumps the version by one and emits one `modified` event. A modify that sets the same value changes nothing. Setting `none` clears the recorded time. A modify of the value sends no email. It is allowed only on a `booked` reservation and fails with `invalid_transition` on `seated`, `attended`, `cancelled`, and `no_show`, and with `invalid_request` on an erased reservation. A key without `write` cannot set it. `declined` leaves the reservation booked and its tables held. The engine sends no reconfirmation request. Reads through get, list, search, and agenda return the stored value. Erasure and retention reset it to `none` and null.

## C26. Seating needs a table

A move to `seated` fails with `table_required` when the reservation holds no active table, as an overbooked booking does not. Nothing is written: the status stays `booked`, the version does not change, and no `seated` event is emitted. The same idempotency key can be sent again after staff assign a table. Staff assign a table with a modify of `tables`. The exclusion constraint checks it, so a table that another booking holds fails with `slot_taken` and the booking stays without tables. After a free table is assigned, the move to `seated` succeeds. A booked reservation that holds tables seats as before, and a replay of the same key returns the original version without a second event. A walk-in is seated at once with its tables and is unchanged. The moves to `attended` and `no_show` are unchanged, and a `no_show` of a booking without tables is allowed. `invalid_transition` is reported before `table_required`, so a cancelled booking fails with `invalid_transition`. A modify that would leave a `seated` reservation without tables fails with `table_required` and changes nothing.

## C27. Staff invitations

A venue `admin` with a staff session creates an invitation with a `role` of `read`, `write`, or `admin`, an optional `email`, and an optional `expiresInHours` from 1 to 336, default 72. The response carries the invitation and a one-time `token`. No later read returns the token, and the engine stores only a hash of its secret. Any other role, a malformed email, or a bad expiry fails with `invalid_request` and creates nothing. A `read` or `write` session, and a key of any role, an `admin` key included, fail with `forbidden` on create, list, and revoke, and change nothing. The list shows each invitation as `pending`, `redeemed`, `revoked`, or `expired`, newest first, without the token. A revoke makes the token useless, is repeatable, and fails with `invitation_redeemed` on a redeemed invitation. A signed-in account redeems with the token and gains the invited role in that venue. An account that is already a member never loses a role, and gains a higher one. A person without an account signs up with the token in the `X-Invitation-Token` header and gains the same membership, under `SIGNUP=open`, `first-user`, and `closed`. That sign-up creates no venue and does not take the first-user mark. Without the header `SIGNUP=closed` still refuses with `SIGNUP_CLOSED`. A token that does not work in a sign-up fails with `INVALID_INVITATION` and creates no account, in every mode. An invitation works once. Of any number of concurrent redemptions, by sign-up or by a signed-in account, exactly one succeeds, one membership is written, and at most one account is created. A redemption that races a revoke ends with the invitation redeemed or revoked, never both. An unknown id, a wrong secret, and an expired, used, or revoked invitation, and one bound to another email, return the same `invalid_invitation` answer, which names no venue. An email-bound invitation is held for that address, compared without regard to case, and the wrong address leaves it pending. An invitation never reveals or changes another venue: a revoke through another venue's path fails with `invitation_not_found`, and the list shows only the venue's own. Retention deletes an invitation 30 days after it expires, in any state, and keeps the membership it created. Deleting the venue deletes its invitations.

## C28. Rate limits on credential paths

A client address that spends its budget of limited calls inside a window is refused with `429`, the code `rate_limited` and a `Retry-After` header in whole seconds, and the refused call does no work. The limited calls are every write under `/api/auth` other than sign-up, every sign-up, and invitation redemption. A sign-up that carries a non-empty `X-Invitation-Token` header counts on the sign-up budget and on the invitation budget, and when either is spent the call is refused and neither is charged. Each kind has its own budget, set by `RATE_LIMIT_AUTH`, `RATE_LIMIT_SIGNUP` and `RATE_LIMIT_INVITATION` as a maximum over a window, with defaults of 30 per 15 minutes, 5 per hour and 10 per 15 minutes. A refused call does not extend the window, and a call after the window ends is allowed. Budgets are per client address, so a refused address does not affect another. A path spelled with repeated or trailing slashes is limited like the plain one. The refusal is identical for every call over the limit, whatever account, password or token the body names, so it never shows whether one exists. A refused sign-up creates no account. `GET`, `HEAD` and `OPTIONS` calls, `/health` and every other `/v1` route are never limited. With `TRUST_PROXY=true` the address is the last `X-Forwarded-For` entry and, when that is missing or not an address, the socket address. Otherwise it is the socket address and the header is ignored. `RATE_LIMIT=off` turns the limits off, and an invalid setting stops the API at startup.

## C29. Venue creation limit

Under `SIGNUP=open`, any signed-in account creates a venue with `POST /v1/venues` and becomes its `admin`, an invited account included. Under `SIGNUP=first-user` and `SIGNUP=closed`, only the owner, the account marked at sign-up under `first-user`, creates a venue, and may create any number of them. Any other account fails with `403` and `venue_creation_closed`, and no venue is written. That covers an account invited as `read`, `write`, or `admin`, an account added to a venue by other means, and an account that already administers a venue. The check runs before the body is validated. A request with no session fails with `unauthorized`. An API key of any role never creates a venue: a request with only a key fails with `unauthorized` in every mode, and a key sent beside a session neither grants nor removes the right to create. A refused account keeps its access: `GET /v1/venues` still lists the venues it belongs to, and its role in them still works. The mode is read on every request, so changing `SIGNUP` changes the answer without a schema change. Existing accounts, venues, memberships, keys, and invitations are untouched. An instance whose accounts were created under `open` has no owner, so under `first-user` or `closed` nobody creates a venue until the operator marks one account, with SQL or by reopening sign-up for a while.

## C30. Venue members

A venue `admin` with a staff session lists the venue's members and removes one. The list shows `userId`, `name`, `email`, and `role` for each member of that venue and nothing else, ordered by email. It shows no member of another venue. A `read` or `write` session, and a key of any role, an `admin` key included, fail with `forbidden` on list and remove, and change nothing. A request for a venue the caller does not belong to fails with `venue_not_found`. A remove deletes one membership and returns its `userId` and `role`. The removed person's next request to that venue, read or write, fails with `venue_not_found` when they still belong to another venue, and with `unauthorized` when no membership is left, because C32 revokes their sessions. Their account and their memberships in other venues are untouched. Keys they made and sessions are handled as C32 states. A `userId` that is unknown, and one that is a member of another venue only, fail with `member_not_found`, the same answer, and change nothing. A second removal of the same person fails with `member_not_found`. A venue always keeps at least one `admin`. A removal that would leave none fails with `last_admin` and changes nothing, including an admin who removes themselves as the only admin, and including when other members remain. An admin who removes themselves while another admin remains succeeds. Of two admins who remove each other at once, and of three who remove each other in a ring, at least one admin remains, and exactly one of the two removals succeeds. A removed person invited again redeems the new invitation and has a membership again. The invitation that first created the membership stays redeemed and does not work a second time. A removal is not recorded in the event feed. There is no role change.

## C31. Membership audit

Each change of access writes one row to a venue-scoped, append-only log, in the same transaction as the change. Creating an invitation writes `invited` with the admin as actor, the invitation id and the role. A revoke that revokes writes `invite_revoked` with the same fields. A redemption writes `redeemed` with no actor, the redeemer as target, the invitation id and the invited role, for a signed-in account and for a sign-up alike. A removal writes `member_removed` with the admin as actor, the removed account as target and the removed role. A repeated revoke, a revoke of a redeemed or foreign invitation, a refused or unknown removal, and a refused redemption write no row. Of any number of concurrent redemptions of one invitation, exactly one `redeemed` row is written. A venue's rows are never mixed with another's. A row holds account and invitation ids and a role, and never an email, a name or a token. Deleting an account keeps its rows. Retention deletes a venue's rows older than its `retentionDays` and keeps newer ones, per venue, in bounded batches. C32 adds the read route.

## C32. Member removal revocation and audit read

A removal does more than delete the membership, and all of it happens in the transaction of C30, so it is all or nothing. It revokes the API keys that the removed person made in this venue with a staff session. A key they made for this venue is gone, and a key of theirs that also holds another venue keeps that other grant. A key made by someone else, a key made with an `admin` key, a key made before this case, and a key of the same person in another venue are not touched. It revokes every session of the removed person when no membership remains. When the person still belongs to another venue it revokes none, because a session belongs to the account, and their other venues keep working. It sets `creatorDepartedAt` on the webhook endpoints the person made in this venue and does not delete or disable them, so they keep delivering. The webhook list returns `creatorDepartedAt`, a timestamp or null, and never the creator's id. An endpoint made by someone else, made with a key, made before this case, or in another venue stays null. A removal that fails after any step, including a failed audit write, leaves the membership, the keys, the sessions, and the webhooks unchanged and writes no audit row. A removal refused with `last_admin` or `member_not_found` revokes nothing and writes no audit row. The response is `{ member, revoked }`, with counts `keys`, `sessions`, and `webhooksFlagged`.

`GET /v1/venues/{venueId}/audit` reads the membership audit log of C31. It is open to an `admin` session and an `admin` key. A `read` or `write` session or key fails with `forbidden`, a caller outside the venue fails with `venue_not_found`, and a request with no credentials fails with `unauthorized`. It returns `{ entries, nextCursor }` newest first, each entry with `id`, `action`, `actorUserId`, `targetUserId`, `invitationId`, `role`, and `occurredAt`, with `limit` from 1 to 200, default 50. Following `nextCursor` visits every entry once, and the last page has a null cursor. A bad `limit`, a malformed `cursor`, and a cursor from another venue fail with `invalid_request`. The log shows only its venue's entries and no row holds an email, a name, an invitation token, a key, or a webhook URL or secret. Keys, endpoints, and sessions made before this case have no recorded creator and are not reached.

## C33. Public profile and JSON-LD

A venue publishes structured local data that is separate from its private data. `GET /v1/venues/{venueId}/public.jsonld` needs no credentials. It returns `404` with `venue_not_found`, the same body and headers, for an unknown venue and for a venue whose `publicProfileEnabled` is off, which is the default. When it is on, the answer is `application/ld+json` with `@context` `https://schema.org`, `@type` `Restaurant`, the venue name, a `PostalAddress`, and the optional telephone, url, cuisine, price range and geo that the venue set. It holds one `openingHoursSpecification` entry per service of that venue with `opens` and `closes` equal to the service times and all seven days. It holds a `ReserveAction` only when a `bookingUrl` is set. It never holds `noticeAddress`, an email, a key, another venue's data or guest data. The answer has an `ETag`, `Cache-Control: public, max-age=300`, and `Access-Control-Allow-Origin: *`, and a matching `If-None-Match` gets `304`.

`PUT /v1/venues/{venueId}/public-profile` is admin only (`forbidden` for any other role, `venue_not_found` for another venue, `unauthorized` with no credentials). It is partial, and `null` clears a field. It fails with `invalid_request` for a URL that is not `https`, a country that is not a supported upper-case ISO 3166-1 alpha-2 code, a string over its limit, a malformed phone or price range, and a coordinate out of range. It fails with `public_profile_incomplete` when enabling without a venue name, street, locality and country, or when only one of latitude and longitude is set. Reads of the fields round-trip.
