# Conformance cases

These are the acceptance tests for the contract. Each case states the observable behavior. They assert behavior, not storage internals. The storage-level mutant sweep of the overlap predicate is a separate test, not listed here.

A case is satisfied when a conforming engine produces the stated result. The ids are stable and referenced by the requirements.

## C1. One transaction

Two concurrent creates for the same venue, date, time, and table produce exactly one booking and one `slot_taken`. The loser never double-books the table.

## C2. Idempotent create

Replaying a create with the same idempotency key returns the original reservation id and version. No second reservation exists. A replay returns the stored answer even when the rules or the clock have since changed: after the date is blocked, or after the start moves inside the lead time, the same key still returns the original id and version, while a new key for the same request is refused with `date_blocked` or `lead_time_violation`. The hours, lead time, horizon, blocked date and table checks refuse a first attempt only.

## C3. Snapshot is not a hold

Availability returns a free slot. A create for that slot then either fails with `slot_taken` or assigns a different eligible table. It never double-books, and a failed create writes nothing. A create with explicit tables that are no longer free fails with `slot_taken`. Explicit tables must be distinct tables of the venue: an unknown id, an id of another venue, or a repeated id fails with `invalid_request` on create, walk-in and modify, and writes nothing.

## C4. Modify bumps the version

A modify that changes a field produces a version one greater than before. A no-op modify produces no new version. The confirmation is sent once for the new version when the modify carries `partySize` or `tables`. A modify with only consent, rating, the booking note, or reconfirmation sends no email.

A modify that changes only consent, rating, or the booking note is allowed on `booked`, `seated` and `attended`. A change to party size or tables is allowed only on `booked` and `seated`, and fails with `invalid_transition` otherwise. A change to reconfirmation is allowed only on `booked`. `cancelled` and `no_show` reject every modify.

## C5. Erasure

Erasure by guest id returns the counts of erased reservations, guest records, and waitlist entries, and no personal value remains for that guest. The guest id is the record id read from `guest.guestId`. Erasure deletes the guest record and any guest merged into it, and `erasedGuests` reports how many. Each erased reservation keeps its date, party size, and status, with no guest linked, and reads `guestLocale` null (ADR-0024). It deletes the venue's waitlist entries whose contact normalizes to the guest's keys and leaves other venues and other guests untouched. A guest id from another venue erases nothing. A guest id that is not a record is read as a contact, a deprecated fallback, and a contact that matches no record reports `erasedGuests` 0. Erasure by principal blanks the reservations that principal owns, then deletes every guest record of the venue that was linked to them and has no remaining reservation that is not erased, with the guests merged into it. A guest with a visit owned by another principal stays, and `erasedGuests` counts the records deleted. Each tombstone it emits carries a hash of the reservation id, visible in the event feed.

## C6. Notice address

Enabling a venue without a notice address via `venue.setConfig` fails with `notice_address_required`. Clearing the address while the venue is enabled fails. A venue already enabled without one stays enabled.

## C7. Party size

A party above the venue maximum fails with `party_size_too_large`. A party that fits no table combination fails with `no_suitable_table`.

## C8. Hours

A time outside the hours, off the slot grid, or after the last seating fails with `outside_hours`. A time within the lead time fails with `lead_time_violation`.

## C9. Status transitions

`reservation.status` moves a reservation to seated, attended, or no_show and emits an event. A transition that is not allowed fails with `invalid_transition`. Cancelling twice returns `already_cancelled` on the second call.

## C10. Venue isolation

A request scoped to one venue never returns data from another venue. A request for a venue the caller cannot see returns `venue_not_found`, the same as an unknown venue.

## C11. Event feed

A consumer that polls the feed from a cursor sees events with stable, monotonic ids and no gap. Replaying from an earlier cursor re-emits the same ids, which the consumer deduplicates.

## C12. Attribution

The engine sets `basis`, `owner_principal`, and `booked_via` from the authenticated channel. A write that tries to set them is ignored, and the stored value comes only from the channel.

## C13. Cursor expiry

Polling the event feed with a cursor older than the venue's retention period fails with `expired_cursor`. A cursor within the retention period returns no gap in the event ids.

## C14. Consent

A reservation carries `guest.consent`, one of `unknown`, `granted`, or `denied`. A create or walk-in without it returns `unknown` and no `consentRecordedAt`. A value outside the three fails with `invalid_request`. A modify that changes consent bumps the version by one and emits one `modified` event. A modify that sets the same value changes nothing. Consent changing to `granted` or `denied` sets `consentRecordedAt`. Reads through get, list, search, and agenda return the stored value. Erasure resets consent to `unknown` and clears `consentRecordedAt`, and its counts still report reservations and guests erased.

## C15. Webhooks

Registering an https endpoint returns `201` with its id and a secret, and the secret never appears in a listing. A new endpoint receives only events written after registration. Each event arrives as a POST whose `OpenCovers-Signature` verifies with HMAC-SHA256 of `<t>.<raw body>` under the secret and fails under any other key. Events reach an endpoint in id order. A failed delivery stops that endpoint, retries the same event after `min(30s × 2^(failures − 1), 1h)`, and on success resumes without skipping or repeating acknowledged events. A failing or slow endpoint does not delay another. Two workers running at once deliver each event to an endpoint exactly once. A cursor behind the retention watermark jumps to it and records the drop in `lastError`. A URL that is not https, carries credentials, or resolves to a loopback, private, link-local, CGNAT, unspecified, or multicast address, in IPv4, IPv6, or IPv4-mapped form, fails with `webhook_url_rejected`. A host that resolves to such an address at delivery time is not contacted. A venue holds at most 5 endpoints, and a webhook id from another venue returns `webhook_not_found`.

## C16. Rating

A reservation carries `rating`, an integer from 1 to 5 or null, and `ratingRecordedAt`, a timestamp or null. A create or walk-in without it returns both as null. A value outside 1 to 5, a non-integer, or a string fails with `invalid_request`. A modify that changes the rating bumps the version by one and emits one `modified` event. A modify that sets the same value changes nothing. Setting null clears the rating and `ratingRecordedAt`. A key without `write` cannot set it. Reads through get, list, search, and agenda return the stored value. Erasure resets both to null.

## C17. Guest identity

A create, walk-in, or seated waitlist entry with a contact returns `guest.guestId`. Two bookings in one venue whose contacts normalize to the same key return the same `guestId`. An email that differs only in case or surrounding whitespace is the same key. Dots and `+` tags are different keys. A phone without a country code is read with the venue's `phoneCountry`, or the country of its time zone when that is null, so `600 123 456` and `+34 600 123 456` match in Spain. The name never matches. The same contact in two venues returns two different ids. A booking without a contact, or with a contact that does not normalize, succeeds and returns no `guestId`. Concurrent bookings for one new contact produce exactly one guest. Consent and rating stay on each reservation. A `phoneCountry` that is not a supported upper-case ISO 3166 alpha-2 code fails with `invalid_request`.

## C18. Guest retention

A guest whose latest visit is older than the venue's retention period, with no visit ending inside that period and no future booking, expires on the next retention run. A cancelled booking is not a visit and not a future booking here, and a booking that has not started yet counts as a visit at the moment it was made, so `lastVisitAt` is never later than now (C61). Its record keeps its id and holds no email, phone, or name. Each reservation linked to it is blanked and unlinked as erasure does, keeps its date, party size, and status, reads `guestLocale` null, and emits one `erased` event whose tombstone hash is the hash of the reservation id. A guest merged into it expires with it. A reservation with no guest record that holds a name, a contact, or a booking note and ended before the period is blanked the same way, `guestLocale` included, with one `erased` event, and one that ends inside the period, ends in the future, or is booked or seated and not yet over stays. Waitlist entries older than the period are deleted. A guest inside the period stays, each venue uses its own period, and other venues are untouched. A reservation linked to a guest is left to guest expiry. A second run changes nothing, and two runs at once expire each guest once.

## C19. Guest merge

A key or session that can read the venue lists its guests by latest visit, then id, and pages through them with a cursor without gaps or repeats. It filters by a normalized contact or a name prefix. A guest merged into another or cleared by retention is not listed, and reading it fails with `guest_not_found`, as does a guest id of another venue. Reading a guest returns its visit count, first and latest visit, and the ids and statuses of the reservations it holds. Only an admin merges and unmerges, and a `read` or `write` key fails with `forbidden`. Merging B into A moves every reservation of B to A in one transaction, sets A's latest visit to the later of the two, and keeps B merged into A. Repeating the Idempotency-Key applies the merge once. Merging a guest into itself fails with `invalid_request`, a guest of another venue or a cleared guest fails with `guest_not_found`, and a source or target already merged fails with `guest_merged`, so A into B after B into A is rejected. A later booking with B's contact links to A. Unmerging B returns exactly the reservations moved at merge time, leaves later ones with A, and recomputes A's latest visit. A second unmerge and an unmerge of a guest never merged fail with `guest_not_merged`. Erasure by guest id, erasure by principal, and retention leave no personal value of the guests involved in the guest audit, and the merge can no longer be undone.

## C20. Availability explanation

A key or session that can read the venue asks why a date, time, and party size, with an optional zone, is or is not bookable. The answer has `available` and a list of reasons, empty when the time is bookable. Each reason has a `code` from the error vocabulary, a `message`, and `details`. A time outside every service returns `outside_hours` with the service hours. A time off the slot grid returns `outside_hours` with the interval and the grid times before and after it. A time after the last seating returns `outside_hours` with the last seating time. A time within the lead time returns `lead_time_violation` with the lead time and the earliest bookable date and time. A party above the capacity of the venue, or of the zone, returns `party_size_too_large` with the largest party. A party that the free tables cannot seat returns `no_suitable_table` with the counts of free and total tables, the free seats, and the largest free table. Several reasons come in that order, and a create for the same request fails with the code of the first. `available` is true exactly when a create would succeed and availability lists the time as free. A blocked time returns up to 3 nearest available times that day, nearest first, each of them bookable. The answer never contains a guest name, contact, reservation id, or table id. An unknown venue, or one the caller cannot see, returns `venue_not_found`.

## C21. Turn time and party limits

A venue sets `turnTimes` in its config, rows of `upTo` and `minutes` with `upTo` strictly increasing, at most 10 rows, and minutes from 15 to 480. A booking holds its tables for the minutes of the first row whose `upTo` is at least the party size, or of the last row for a larger party. With no rows it holds them for 120 minutes, and an empty array clears the rows. A walk-in uses the same turn time. With rows of 2 for 90, 4 for 120, and 8 for 150, a party of 2 booked at 20:00 frees its table at 21:30, a party of 4 at 22:00, and a party of 8 or more at 22:30. The requested booking is sized by its own party, so with a party of 2 at 22:00 a party of 2 fits at 20:30 and a party of 8 does not fit at 20:00. A service sets `minPartySize` and `maxPartySize`, integers of at least 1. A create below the minimum fails with `party_size_too_small`, above the maximum with `party_size_too_large`, and availability shows the time as unavailable. The explanation returns the reason with rule `service_limit`, the service, the party size, and the limit, after `lead_time_violation` and before the capacity and table reasons. A walk-in is not held to the limits. Null clears a limit, and a limit left out of an update keeps its value. A minimum above the maximum, a limit that is not an integer of at least 1, and malformed turn times fail with `invalid_request` and change nothing. A service without limits and a venue without turn times behave as before. Availability, create, and the explanation agree for every time and party size. Settings stay in their venue, and a `read` key cannot change them.

## C22. Role boundaries

Every venue route accepts a key or a staff session with a role for that venue, `read`, `write`, or `admin`. A `read` role cannot write anything. A `write` role creates, walks in, modifies, cancels, and moves reservations, including consent and rating, adds, seats, and cancels waitlist entries, and manages webhooks. Changing the venue config, creating, updating, or deleting a service, a table, a floor item, or its layout, minting, listing, or revoking API keys, merging or unmerging guests, and erasing guest data need `admin`. A `read` or `write` key or session that tries one fails with `forbidden`, and the config, services, tables, floor items, and keys read back unchanged. A refused erasure leaves the guest data unchanged. A session follows the same rule by its venue role. A `POST`, `PUT`, `PATCH` or `DELETE` under `/v1/`, other than `/v1/public/`, that carries a cookie and no `apikey` fails with `403 forbidden` when it sends an `Origin` that is not `BETTER_AUTH_URL` or a `TRUSTED_ORIGINS` entry, `null` included, and with `invalid_request` when it has a body whose media type is not `application/json`, and it writes nothing. The same write with JSON from a trusted origin, or with no `Origin`, works, and so does a write with no body. Reads, `apikey` requests, whatever their `Origin` and content type, and the public routes are unaffected. A request body over 256 KB fails with `invalid_request` on every route, before authentication, and the API stops reading it at the limit.

## C23. Booking note

A reservation carries `commentary`, a string of at most 500 characters after trimming, empty when no note was given. A create or walk-in without it returns an empty string. A value that is not a string, or longer than 500 characters, fails with `invalid_request`. A modify that changes the note bumps the version by one and emits one `modified` event, sends no email, and may set it on an attended reservation. A modify that sets the same value changes nothing, and an empty string clears it. A key without `write` cannot set it. A modify on an erased reservation fails with `invalid_request`. Reads through get, list, search, and agenda return the stored value. Erasure and retention reset it to an empty string. The note is free text for staff and never holds health data, and the contract says so.

## C24. Overbooking ceiling

A venue has `overbookingCeiling` in its config, an integer from 0 to 1000, default 0. Any other value fails with `invalid_request`, changes nothing, and only an `admin` key sets it. At 0 a create that finds no free table combination fails with `no_suitable_table`, and a modify that would leave a booking without tables fails with it too. Above 0 a create that fits the venue but finds no free table combination is accepted when the party sizes of every `booked` or `seated` booking without tables whose window overlaps the new one, plus the new party, are at most the ceiling. The booking has `tables: []`, version 1, status `booked`, and holds no row in the table allocations. The next create that would pass the ceiling fails with `no_suitable_table`. A booking that is cancelled, attended, or a no-show stops counting. A booking that does not overlap does not count. The ceiling never admits a party larger than the venue, which keeps `party_size_too_large`, a create that names tables another booking holds, which keeps `slot_taken`, or a walk-in, which keeps `no_suitable_table`. Availability and the explanation show a time as bookable exactly when a create would succeed. Staff give the booking tables with a modify, and the database exclusion constraint still refuses a table that another booking holds, with `slot_taken`. A modify that raises the party of a booking without tables, or releases its tables, passes the same ceiling check. Concurrent creates never take more than the ceiling in total. A ceiling in one venue does not change another venue.

## C25. Reconfirmation

A reservation carries `reconfirmation`, one of `none`, `requested`, `confirmed`, `declined`, or `no_answer`, and `reconfirmationRecordedAt`, a timestamp or null. A create without it returns `none` and null. A create with a value returns it with a recorded time, and `none` records no time. Any other value, or a value that is not a string, fails with `invalid_request`, and so does a walk-in that carries the field. A modify that changes the value bumps the version by one and emits one `modified` event. A modify that sets the same value changes nothing. Setting `none` clears the recorded time. A modify of the value sends no email. It is allowed only on a `booked` reservation and fails with `invalid_transition` on `seated`, `attended`, `cancelled`, and `no_show`, and with `invalid_request` on an erased reservation. A key without `write` cannot set it. `declined` leaves the reservation booked and its tables held. The engine sends no reconfirmation request. Reads through get, list, search, and agenda return the stored value. Erasure and retention reset it to `none` and null.

## C26. Seating needs a table

A move to `seated` fails with `table_required` when the reservation holds no active table, as an overbooked booking does not. Nothing is written: the status stays `booked`, the version does not change, and no `seated` event is emitted. The same idempotency key can be sent again after staff assign a table. Staff assign a table with a modify of `tables`. The exclusion constraint checks it, so a table that another booking holds fails with `slot_taken` and the booking stays without tables. After a free table is assigned, the move to `seated` succeeds. A booked reservation that holds tables seats as before, and a replay of the same key returns the original version without a second event. A walk-in is seated at once with its tables and is unchanged. The moves to `attended` and `no_show` are unchanged, and a `no_show` of a booking without tables is allowed. `invalid_transition` is reported before `table_required`, so a cancelled booking fails with `invalid_transition`. A modify that would leave a `seated` reservation without tables fails with `table_required` and changes nothing.

## C27. Staff invitations

A venue `admin` with a staff session creates an invitation with a `role` of `read`, `write`, or `admin`, an optional `email`, and an optional `expiresInHours` from 1 to 336, default 72. The response carries the invitation and a one-time `token`. No later read returns the token, and the engine stores only a hash of its secret. Any other role, a malformed email, or a bad expiry fails with `invalid_request` and creates nothing. A `read` or `write` session, and a key of any role, an `admin` key included, fail with `forbidden` on create, list, and revoke, and change nothing. The list shows each invitation as `pending`, `redeemed`, `revoked`, or `expired`, newest first, without the token. A revoke makes the token useless, is repeatable, and fails with `invitation_redeemed` on a redeemed invitation. A signed-in account redeems with the token and gains the invited role in that venue. An account that is already a member never loses a role, and gains a higher one. A person without an account signs up with the token in the `X-Invitation-Token` header and gains the same membership, under `SIGNUP=open`, `first-user`, and `closed`. That sign-up creates no venue and does not take the first-user mark. Without the header `SIGNUP=closed` still refuses with `SIGNUP_CLOSED`. A token that does not work in a sign-up fails with `INVALID_INVITATION` and creates no account, in every mode. An invitation works once. Of any number of concurrent redemptions, by sign-up or by a signed-in account, exactly one succeeds, one membership is written, and at most one account is created. A redemption that races a revoke ends with the invitation redeemed or revoked, never both. An unknown id, a wrong secret, and an expired, used, or revoked invitation, and one bound to another email, return the same `invalid_invitation` answer, which names no venue. An email-bound invitation is held for that address, compared without regard to case, and the wrong address leaves it pending. A caller with no session asks `POST /v1/invitations/check` with a token and gets `{ valid: true }` for an invitation that could be redeemed now, an email-bound one included, and `{ valid: false }` for an unknown id, a wrong secret, a malformed token, and an expired, used, or revoked invitation, the same body for every cause, with no venue, role, email, or reason. A missing or empty token fails with `invalid_request`. The check claims nothing and writes nothing, so it leaves the invitation pending, and it agrees with a redemption made at the same moment. It spends the invitation budget of C28 with redemptions and token sign-ups. An invitation never reveals or changes another venue: a revoke through another venue's path fails with `invitation_not_found`, and the list shows only the venue's own. Retention deletes an invitation 30 days after it expires, in any state, and keeps the membership it created. Deleting the venue deletes its invitations.

## C28. Rate limits on credential paths

A client address that spends its budget of limited calls inside a window is refused with `429`, the code `rate_limited` and a `Retry-After` header in whole seconds, and the refused call does no work. The limited calls are every write under `/api/auth` other than sign-up, every sign-up, invitation redemption, and venue creation (`POST /v1/venues`). A sign-up that carries a non-empty `X-Invitation-Token` header counts on the sign-up budget and on the invitation budget, and when either is spent the call is refused and neither is charged. Each kind has its own budget, set by `RATE_LIMIT_AUTH`, `RATE_LIMIT_SIGNUP` and `RATE_LIMIT_INVITATION` as a maximum over a window, with defaults of 30 per 15 minutes, 5 per hour and 10 per 15 minutes. Venue creation has its own budget, set by `RATE_LIMIT_VENUE_CREATION`, default 10 per hour. It is checked before the session and the body are read, so a venue-creation call that fails with `unauthorized`, `venue_creation_closed` or `invalid_request` spends budget like one that succeeds, and a refused one creates no venue. The route takes no `Idempotency-Key`, so a repeated call counts like any other. `POST /v1/venues` is limited with a repeated or trailing slash too, and `GET /v1/venues` is not limited. A refused call does not extend the window, and a call after the window ends is allowed. Budgets are per client address, so a refused address does not affect another. A path spelled with repeated or trailing slashes is limited like the plain one. The refusal is identical for every call over the limit, whatever account, password or token the body names, so it never shows whether one exists. A refused sign-up creates no account. `GET`, `HEAD` and `OPTIONS` calls, `/health` and every other `/v1` route, other than `POST /v1/venues`, are never limited. With `TRUST_PROXY=true` the address is the last `X-Forwarded-For` entry and, when that is missing or not an address, the socket address. Otherwise it is the socket address and the header is ignored. An IPv6 address is counted by its first 48 bits. Each rule tracks at most 10,000 clients. A spent budget stays spent however many new addresses arrive, and while a rule tracks its most clients a new client is refused with `rate_limited` and a `Retry-After` until the oldest window ends. `RATE_LIMIT=off` turns the limits off, and an invalid setting stops the API at startup. C52 adds limits on the routes under `/v1/public/`, `GET` included.

## C29. Venue creation limit

Under `SIGNUP=open`, any signed-in account creates a venue with `POST /v1/venues` and becomes its `admin`, an invited account included. Under `SIGNUP=first-user` and `SIGNUP=closed`, only the owner, the account marked at sign-up under `first-user`, creates a venue, and may create any number of them. Any other account fails with `403` and `venue_creation_closed`, and no venue is written. That covers an account invited as `read`, `write`, or `admin`, an account added to a venue by other means, and an account that already administers a venue. The check runs before the body is validated. A request with no session fails with `unauthorized`. An API key of any role never creates a venue: a request with only a key fails with `unauthorized` in every mode, and a key sent beside a session neither grants nor removes the right to create. A refused account keeps its access: `GET /v1/venues` still lists the venues it belongs to, and its role in them still works. The mode is read on every request, so changing `SIGNUP` changes the answer without a schema change. Existing accounts, venues, memberships, keys, and invitations are untouched. An instance whose accounts were created under `open` has no owner, so under `first-user` or `closed` nobody creates a venue until the operator marks one account, with SQL or by reopening sign-up for a while.

## C30. Venue members

A venue `admin` with a staff session lists the venue's members and removes one. The list shows `userId`, `name`, `email`, and `role` for each member of that venue and nothing else, ordered by email. It shows no member of another venue. A `read` or `write` session, and a key of any role, an `admin` key included, fail with `forbidden` on list and remove, and change nothing. A request for a venue the caller does not belong to fails with `venue_not_found`. A remove deletes one membership and returns its `userId` and `role`. The removed person's next request to that venue, read or write, fails with `venue_not_found` when they still belong to another venue, and with `unauthorized` when no membership is left, because C32 revokes their sessions. Their account and their memberships in other venues are untouched. Keys they made and sessions are handled as C32 states. A `userId` that is unknown, and one that is a member of another venue only, fail with `member_not_found`, the same answer, and change nothing. A second removal of the same person fails with `member_not_found`. A venue always keeps at least one `admin`. A removal that would leave none fails with `last_admin` and changes nothing, including an admin who removes themselves as the only admin, and including when other members remain. An admin who removes themselves while another admin remains succeeds. Of two admins who remove each other at once, and of three who remove each other in a ring, at least one admin remains, and exactly one of the two removals succeeds. A removed person invited again redeems the new invitation and has a membership again. The invitation that first created the membership stays redeemed and does not work a second time. A removal is not recorded in the event feed. C37 adds the role change.

## C31. Membership audit

Each change of access writes one row to a venue-scoped, append-only log, in the same transaction as the change. Creating an invitation writes `invited` with the admin as actor, the invitation id and the role. A revoke that revokes writes `invite_revoked` with the same fields. A redemption writes `redeemed` with no actor, the redeemer as target, the invitation id and the invited role, for a signed-in account and for a sign-up alike. A removal writes `member_removed` with the admin as actor, the removed account as target and the removed role. A repeated revoke, a revoke of a redeemed or foreign invitation, a refused or unknown removal, and a refused redemption write no row. Of any number of concurrent redemptions of one invitation, exactly one `redeemed` row is written. A venue's rows are never mixed with another's. A row holds account and invitation ids and a role, and never an email, a name or a token. Deleting an account keeps its rows. Retention deletes a venue's rows older than its `retentionDays` and keeps newer ones, per venue, in bounded batches. C32 adds the read route.

## C32. Member removal revocation and audit read

A removal does more than delete the membership, and all of it happens in the transaction of C30, so it is all or nothing. It revokes the API keys that the removed person made in this venue with a staff session. A key they made for this venue is gone, and a key of theirs that also holds another venue keeps that other grant. A key made by someone else, a key made with an `admin` key, a key made before this case, and a key of the same person in another venue are not touched. It revokes every session of the removed person when no membership remains. When the person still belongs to another venue it revokes none, because a session belongs to the account, and their other venues keep working. It sets `creatorDepartedAt` on the webhook endpoints the person made in this venue and does not delete or disable them, so they keep delivering. The webhook list returns `creatorDepartedAt`, a timestamp or null, and never the creator's id. An endpoint made by someone else, made with a key, made before this case, or in another venue stays null. A removal that fails after any step, including a failed audit write, leaves the membership, the keys, the sessions, and the webhooks unchanged and writes no audit row. A removal refused with `last_admin` or `member_not_found` revokes nothing and writes no audit row. The response is `{ member, revoked }`, with counts `keys`, `sessions`, and `webhooksFlagged`.

`GET /v1/venues/{venueId}/audit` reads the membership audit log of C31. It is open to an `admin` session and an `admin` key. A `read` or `write` session or key fails with `forbidden`, a caller outside the venue fails with `venue_not_found`, and a request with no credentials fails with `unauthorized`. It returns `{ entries, nextCursor }` newest first, each entry with `id`, `action`, `actorUserId`, `targetUserId`, `invitationId`, `role`, `blocklistEntryId` (C56), and `occurredAt`, with `limit` from 1 to 200, default 50. Following `nextCursor` visits every entry once, and the last page has a null cursor. A bad `limit`, a malformed `cursor`, and a cursor from another venue fail with `invalid_request`. The log shows only its venue's entries and no row holds an email, a name, an invitation token, a key, or a webhook URL or secret. Keys, endpoints, and sessions made before this case have no recorded creator and are not reached.

## C33. Public profile and JSON-LD

A venue publishes structured local data that is separate from its private data. `GET /v1/venues/{venueId}/public.jsonld` needs no credentials. It returns `404` with `venue_not_found`, the same body and headers, for an unknown venue and for a venue whose `publicProfileEnabled` is off, which is the default. When it is on, the answer is `application/ld+json` with `@context` `https://schema.org`, `@type` `Restaurant`, the venue name, a `PostalAddress`, and the optional telephone, url, cuisine, price range and geo that the venue set. It holds one `openingHoursSpecification` entry per service of that venue with `opens` and `closes` equal to the service times and the weekdays of that service as `dayOfWeek` (see C36). It holds a `ReserveAction` only when a `bookingUrl` is set. It never holds `noticeAddress`, an email, a key, another venue's data or guest data. The answer has an `ETag`, `Cache-Control: public, max-age=300`, and `Access-Control-Allow-Origin: *`, and a matching `If-None-Match` gets `304`.

`PUT /v1/venues/{venueId}/public-profile` is admin only (`forbidden` for any other role, `venue_not_found` for another venue, `unauthorized` with no credentials). It is partial, and `null` clears a field. It fails with `invalid_request` for a URL that is not `https`, a country that is not a supported upper-case ISO 3166-1 alpha-2 code, a string over its limit, a malformed phone or price range, and a coordinate out of range. It fails with `public_profile_incomplete` when enabling without a venue name, street, locality and country, or when only one of latitude and longitude is set. Reads of the fields round-trip.

## C34. Error retry hint

Every error response carries `retryable`, a boolean, next to `code` and `message`, whatever produced it, including the rate limiter. The value is fixed per `code` and listed in `errors.md`. It is `true` when repeating the same request, unchanged, may succeed later (`rate_limited` after `Retry-After`, `transient`, `idempotency_in_flight`, and `unknown_outcome` with the same idempotency key) and `false` when the caller must change something first (`slot_taken`, `invalid_request`, `forbidden`, `outside_hours`, and the rest). The codes in `errors.md`, in `openapi.yaml`, and in the engine agree. An MCP tool error keeps the text `API error <status>: <code>` and appends ` (retryable)` or ` (not retryable)`, and appends nothing when the response has no `retryable`. Every MCP tool sets `readOnlyHint`, `destructiveHint` and `idempotentHint` explicitly, and every read tool is `readOnlyHint: true`. `docs/contract/mcp.md` lists them.

## C35. Booking policy: horizon, per-guest cap, blocked dates

A venue sets three optional rules in its config. All are off by default, and then every behavior is as before. `maxAdvanceDays` is null or an integer from 0 to 1000. A create for a local date later than today plus that many days, counted in the venue's time zone, fails with `beyond_booking_horizon` (400). A date exactly that many days ahead passes, and a booking just after local midnight uses the local date, not the UTC date. `blockedDates` is a list of at most 366 entries, each a `YYYY-MM-DD` date or a `{ from, to }` range with both ends included. A write replaces the list, an empty list clears it, and overlapping, adjacent and duplicate entries are merged, so a read returns sorted `{ from, to }` ranges. A create on a blocked date fails with `date_blocked` (400), and the dates next to a range stay bookable. `maxActivePerGuestPerDay` is null or an integer from 1 to 100. A create fails with `guest_booking_limit` (409) when the guest, found by the normalized contact, already holds that many `booked` or `seated` bookings on the same local date in the same venue. A booking that is cancelled, attended, or a no-show does not count, the cap is per guest and per venue, and the one booking that reaches the cap passes. A booking without a usable contact has no guest and is not counted. Concurrent creates by one guest on one date never exceed the cap. A walk-in is held to none of the three rules. Availability and the explanation apply the horizon and the blocked dates through the same check as a create, so a time they show as free is a time a create accepts, and the reason a create fails with is the first reason of the explanation. They return `beyond_booking_horizon` with `maxAdvanceDays` and the last bookable date, and `date_blocked` with the blocked range, after `lead_time_violation` and before the service limit. They do not know the guest, so they never apply the cap or the guest blocklist (C57). The cap is checked by create only, ahead of the table search. A modify cannot change the date, so no rule applies to it, and a booking made before a change of policy is never cancelled or altered by it. A value outside the ranges above, a malformed or impossible date, a range whose `from` is after its `to`, an unknown key in an entry, and more than 366 entries fail with `invalid_request` and change nothing. Only an `admin` key sets the policy, and a policy in one venue does not touch another.

## C36. Service weekdays

A service has `days`, a non-empty list of distinct ISO weekdays, 1 (Monday) to 7 (Sunday). It is optional on `POST /v1/venues/{venueId}/services`. A new service without it, and every service that existed before, serves all seven days, so nothing changes until an admin sets it. An update that leaves `days` out keeps the stored value. An empty list, `null`, a value that is not an integer from 1 to 7, a duplicate, and a non-array fail with `invalid_request` and change nothing. A read returns `days` ascending. Only an `admin` key writes it, and a service in one venue does not touch another.

The weekday of a date is the weekday of that calendar date in the venue's time zone, the date the caller names, never the UTC date of the instant. A service serves a time when the time is inside its window and the weekday it opened on is in `days`. An overnight service belongs to the day it opens: with `days` `[5]` and hours 18:00 to 01:00, Friday 23:30 and Saturday 00:30 are served, and Saturday 18:00 and Sunday 00:30 are not. A create, availability and the explanation use the same check. On a day a service does not serve, availability omits that service from its answer, and a create for a time only that service covers fails with `outside_hours`. The explanation gives `outside_hours` with details rule `weekday`, the date, its ISO weekday, and the services that cover the time by hours with their `days`, in the position of the `hours` reason. A time that no service covers by hours still gives rule `hours`. A walk-in is held to the weekday like it is held to the hours: a service that is closed that day takes no walk-in, and it fails with `outside_hours`. Pacing omits a service that does not serve the date. The public `openingHoursSpecification` has one entry per service whose `dayOfWeek` lists only the days of that service, with an overnight service on the day it opens. A create, availability and the explanation agree over a grid of dates and times.

## C37. Member role change

A venue `admin` with a staff session changes a member's role with `PATCH /v1/venues/{venueId}/members/{userId}` and `{ "role": "admin" | "write" | "read" }`. It returns `{ member: { userId, role } }`. The new role applies on the person's next request, in both directions. A `read` or `write` session, and a key of any role, an `admin` key included, fail with `forbidden` and change nothing, a request with no credentials fails with `unauthorized`, and a caller outside the venue fails with `venue_not_found`. A `userId` that is unknown, and one that is a member of another venue only, fail with `member_not_found`, and the other venue's member keeps their role. A role outside the three, an empty role, and a missing role fail with `invalid_request`. Setting the role a member already holds succeeds and writes no audit row. A change writes one `role_changed` row in the transaction of the change, with the admin as actor, the member as target and the new role, and a refused change writes none. A venue always keeps at least one `admin`. A demotion that would leave none, including an admin demoting themselves as the only admin and including when other members remain, fails with `last_admin` and changes nothing. An admin who demotes themselves while another admin remains succeeds. Of two admins who demote each other at once at least one admin remains, and exactly one of the two succeeds. Of three admins who demote each other in a ring at least one remains.

## C38. Venue creator transfer

`GET /v1/account` tells a staff session whether its account is the venue creator, the account that may create venues under `SIGNUP=first-user` and `closed` (C29). A key fails with `forbidden` and no session fails with `unauthorized`. `POST /v1/account/transfer-creator` with `{ "userId" }` moves that mark. Only the current creator may call it. Any other account, a venue `admin` included, and any key, fail with `forbidden`, and no session fails with `unauthorized`, and nothing changes. The target must be a member of at least one venue the caller administers. An unknown account, an account that shares no venue with the caller, and an account that shares only a venue where the caller is not `admin` fail with `member_not_found`, the same answer, and change nothing. A missing, empty or non-string `userId` fails with `invalid_request`. On success the target is the creator and the caller is not, so under `first-user` the caller then fails `POST /v1/venues` with `venue_creation_closed` and the target succeeds. The caller keeps every membership. At every moment exactly one account holds the mark. Of two concurrent transfers by the creator exactly one succeeds and the other fails with `forbidden`. The transfer and its audit rows are one transaction, so a failed audit write leaves the mark where it was. Naming yourself succeeds and writes nothing. A transfer writes one `creator_transferred` row, with the old creator as actor, the new one as target and no role, to each venue that both accounts belong to and where the caller is `admin`. An instance that ran under `open` has no creator, so nobody can call the route until the one-time step of `deploy.md` marks the first one.

C39 to C55 specify the public booking channel of [ADR-0017](../adr/0017-booking-widget-and-self-service-link.md): the online booking settings, the routes under `/v1/public/`, the widget page and the self-service link. They come before the code, and `conformance-status.md` lists them as gaps until each stage lands. Tests that need time use the database clock or set a booking's start, and tests of the form challenge use a low difficulty.

## C39. Online booking settings and the booking key

`GET /v1/venues/{venueId}/online-booking` is open to any role of the venue. A venue that never set it reads `enabled` false, `bookingKey` null, `allowedOrigins` `[]`, `services` and `weekdays` null, `minPartySize` 1, `maxPartySize` 8, `leadTimeMinutes` 0, `maxAdvanceDays` null, `selfServiceCutoffMinutes` 120, `maxOpenBookingsPerContact` 2, `confirmationMode` `auto`, `askConsent` false, `locale` `es`, and the default theme. `PUT` and `POST /v1/venues/{venueId}/online-booking/rotate-key` are admin only. A `read` or `write` key or session fails with `forbidden`, and the settings and the key read back unchanged. A caller outside the venue fails with `venue_not_found`. The `PUT` is partial: an absent field keeps its value, `null` resets a nullable field, `theme: null` resets the theme, and every field round-trips. Each of these fails with `invalid_request` and changes nothing: an origin that is not `https`, or has a path, query, fragment, wildcard or credentials, or is anything other than exactly the origin of that URL (C61); more than 10 origins; a service name the venue does not have; an empty `services` or `weekdays` list; a weekday outside 1 to 7 or repeated; a party limit outside 1 to 100, or a minimum above the maximum; a lead time or cutoff outside 0 to 10080; a horizon outside 0 to 1000; a per-contact cap outside 1 to 20; a locale other than `es`, `en`, `ca`, `fr`, `de`, `it` or `pt`; a theme with an unknown key, a color that is not `#rrggbb`, a radius outside 0 to 24, a font outside the shipped list, or a logo URL that is not `https`, has no host, carries credentials, holds whitespace or a control character, or is over 2048 characters; and a `confirmationMode` of `approval` or of any value other than `auto`. Origins read back with the host in lower case and duplicates merged. A theme whose text color has a contrast below 4.5:1 against its background color saves and returns a `low_contrast` warning, and a color the theme leaves out counts as the widget's built-in one, so a dark background alone warns. The widget sets each theme value as a CSS custom property, one property at a time, after checking it again against the same rules, keeps the built-in value for a key that is absent or fails, and shows the logo as an `<img>` with the venue name as alt text and no referrer, on `/w/{bookingKey}` and on `/r`. No theme value reaches the page as markup, a style attribute or script. Enabling without a venue name, or with no service bookable online (no service in `services`, or any when null, that opens on one of the online `weekdays`), fails with `online_booking_incomplete` and leaves it off. The first enable creates a `bookingKey` of `pk_` and 22 base64url characters, and two venues never share one. Turning online booking off keeps the key, and turning it on again uses the same key. A rotate returns a new key. From the next request the old key answers as an unknown key (C40), with no grace period, and the new key works. A second rotate rotates again. A rotate on a venue that never had a key gives it one and leaves `enabled` false. Turning online booking off and rotating the key end no self-service link (C47). A change in one venue does not touch another, and no change alters an existing booking. In `openapi.yaml`, `confirmationMode` is an open set of values marked with `x-extensible-enum`, not a closed `enum`, and its description tells clients to treat any value other than `auto` as not automatic confirmation. The widget has dark built-in colors for a visitor whose system asks for dark mode. It uses them only on its own pages, `/w/{bookingKey}` and `/r` opened directly and not inside an iframe, and only while the venue's theme sets no color: a theme with any valid color keeps the light built-in colors for every color it leaves out, so a venue's palette is never mixed with the dark one, and a widget framed on a venue's site stays light whatever the visitor's setting, unless the embed asks for dark mode with `?scheme=auto` on the iframe address (`data-scheme="auto"` on the `embed.js` tag). Only the exact value `auto` counts, and a theme with a color still wins over it. The dark built-in colors change no theme value. A theme may also carry `darkColors`, with the same seven keys and the same `#rrggbb` rule as `colors`; an unknown key, a value that is not `#rrggbb` or a `darkColors` that is not an object fails with `invalid_request` and changes nothing, and `{}` is valid. It reads back as saved, with colors in lower case. A widget that follows the visitor's setting shows `darkColors` to a visitor in dark mode, over the dark built-in colors for a key it leaves out and never mixed with `colors`, and shows `colors` over the light built-in ones to a visitor in light mode. A theme may also carry `darkRadius`, an integer from 0 to 24, and `darkFont`, one of the shipped fonts, under the same rules as `radius` and `font` (a value outside them, `null` or another type fails with `invalid_request` and changes nothing). A widget that follows the visitor's setting shows them to a visitor in dark mode, each falling back to `radius` or `font` when absent, and a widget that does not follow the setting ignores them. A dark look is any of `darkColors` (even `{}`), a valid `darkRadius` and a valid `darkFont`: it keeps the widget following the visitor's setting when `colors` is set, and a `colors` without a dark look still keeps it light. A widget that does not follow the setting ignores `darkColors`. Each saved warning carries `palette`, `light` or `dark`. The light warning is as before. The dark warning is made only for a theme with `darkColors`, from its `text` and `background` and the dark built-in text `#f1eee8` and background `#181715` for a key it leaves out, with the same 4.5:1 threshold, and the message begins `The dark text color`. A theme with both palettes below the threshold returns both warnings, light first.

## C40. Public surface and venue isolation

Every guest route sits under `/v1/public/`, and none needs credentials. A request with a staff session cookie, an `apikey` header, or both, gets the same status and body as the same request without them, on the config, availability, create, read, modify and cancel routes, and no public route sets a cookie. An unknown key, a key that does not match the `pk_` format, a rotated key, and the key of a venue with online booking off all give `404` with `venue_not_found`, byte-identical bodies and the same headers, on the config, availability, create and resend routes. A key resolves to one venue, and every read and write under it stays in that venue: a booking made with venue A's key lands in A, and A's key never returns anything of B. The config answer holds the venue's display name, locale and theme, the public profile's phone or null, the online party limits, the weekdays with an online service, the effective lead time and horizon, `askConsent`, `confirmationMode`, a new challenge on every call, `captcha` null unless `PUBLIC_CAPTCHA` is set, `linkResend` (C51), `privacyNoticeUrl` and the venue's `address` (C64), and `zones` (C66). A scan of every public answer, errors included, finds no venue id, reservation id, guest id, table id, zone name other than the venue's effective public zones in the config's `zones` and in availability's `slots[].zones` (C66), service name other than in availability's `slots[].service` while `showServiceNames` is on (C66), `noticeAddress`, API key, booking key other than the one in the path, webhook data, `bookedVia`, `ownerPrincipal` or `basis`, no other guest's name or contact, and no contact of the guest except masked. ## C41. Widget page and framing

`GET /w/{bookingKey}` for an enabled key returns `200` HTML with no `X-Frame-Options` and a `Content-Security-Policy` whose `frame-ancestors` is `'self'` followed by exactly the venue's `allowedOrigins`, or `'none'` when the list is empty. The rest of the policy is the one `openapi.yaml` gives for `widget.page`. The answer sends `X-Robots-Tag: noindex`, `Referrer-Policy: no-referrer` and `X-Content-Type-Options: nosniff`, sets no cookie, and its HTML holds `<meta name="robots" content="noindex">` and no JSON-LD. A change of `allowedOrigins` shows in the header of the next request, and two venues get their own lists. An unknown, rotated or disabled key gets the same `404` HTML page and the same headers, with `frame-ancestors 'none'`. The page loads its hashed assets from `/w/assets/`, which the API serves, and no other file. With `WIDGET_ADDRESS` set, a request for any other host gets that same `404`, and an API whose `WIDGET_ADDRESS` names the staff app's host name refuses to start. A production API without `WIDGET_ADDRESS` serves no widget page. A `lang` query of a supported locale (`es`, `en`, `ca`, `fr`, `de`, `it` or `pt`) sets the page's `<html lang>`, and any other value leaves the venue's locale. The widget has a catalog for each, with the same ids and slots as `es`; if `<html lang>` is not supported it shows `es`. `GET /r`, the self-service page (`widget.selfServicePage`), returns `200` HTML that loads the same assets, with `X-Frame-Options: DENY`, the same policy with `frame-ancestors 'none'` whatever any venue allows, `Cache-Control: no-store`, `X-Robots-Tag: noindex`, `Referrer-Policy: no-referrer` and `nosniff`, and sets no cookie. Its answer is byte-identical whatever query, cookie, key or token header the request carries, apart from a supported `lang`, which sets `<html lang>`. A request for a host other than `WIDGET_ADDRESS` gets the `404` of an unknown key. The page reads the token only from the fragment, removes the fragment from the address bar, keeps the token in memory, and sends it only in `X-Self-Service-Token` with no cookie, so no request URL, body or `Referer` holds it. In the production Caddyfile the staff site block still sends `X-Frame-Options: DENY` and `frame-ancestors 'none'` on every path and answers `/w/*` and `/r` with `404`. The widget site block proxies `/w/*`, `/r` and `/v1/public/*` to the API and serves `/v1/public/*` with `frame-ancestors 'none'`. Test the API headers directly, and the Caddy rules by running the shipped Caddyfile and reading the headers.

`GET /w/embed.js` (`widget.embedScript`) answers `200` with the script, `Content-Type: text/javascript; charset=utf-8`, `Cache-Control: public, max-age=300`, an `ETag` that changes with the content, `X-Content-Type-Options: nosniff` and `Cross-Origin-Resource-Policy: cross-origin`, and no CORS header. A matching `If-None-Match` gets `304`. It answers on the hosts `/w/*` answers on, and with a plain `404` on the staff host, in a production API without `WIDGET_ADDRESS`, and without a widget build. The script adds one iframe of `/w/{data-key}` on its own origin after its tag, with `?scheme=auto` on the address only when the tag has `data-scheme="auto"` exactly (any other value adds nothing, and the value is never copied into the address), and nothing for a `data-key` that is not a booking key or when the same tag runs twice. It sets the iframe's height only from a message whose `origin` is the widget origin, whose `source` is its own iframe, and whose data has exactly `type: "opencovers:height"` and a finite `height` not below 0, kept between 100 and 6000 pixels. A message from another origin or window, with another shape or key, or with `NaN`, an infinite or a negative height changes nothing, and two widgets on one page resize apart. The framed widget page posts only `{type, height}`, with target `*`, when its height changes. Top-level, and on `/r`, it posts nothing.

`GET /v1/public/{bookingKey}/availability?date=&partySize=` returns `{ date, partySize, times }`, the bookable local times in ascending order, each once, and nothing else, except `slots` for a venue with two or more effective public zones or `showServiceNames` on, whose times are exactly `times` (C66). ## C44. Public idempotency

The public create, modify and cancel need an `Idempotency-Key` that is a UUID. A missing key or any other value fails with `invalid_request` and writes nothing. A repeat of a public create's key in the same venue returns the same booking with no second reservation, event or confirmation, even when the challenge's nonce was already used or the challenge is now older than 30 minutes. It returns a new token, after which the earlier token fails with `self_service_link_invalid` and the new one reads the booking. With email on, the repeat sends one `self_service_link` email. A repeat for a booking that is no longer `booked` returns it with `selfServiceToken: null` and leaves its link as it was. Public keys are stored apart from staff keys. When a staff or integration create in the venue used a UUID `K`, a public create with `K` is a new public create: it books its own reservation or fails on its own rules, returns nothing of the staff booking and no token for it, and leaves that booking's link untouched. A staff create with a UUID that a public create used likewise books its own reservation. The same UUID in two venues gives two independent bookings. A public key used for a create and then sent with a modify or a cancel fails with `invalid_request`, as a key of another kind does on the staff routes.

## C45. Bot protection

Each config read returns a new challenge. A public create fails with `invalid_request`, and books and writes nothing, when the `honeypot` field is not empty; when the challenge or the solution is missing; when the challenge is younger than 3 seconds or older than 30 minutes; when any field of the challenge was altered, so its signature does not verify; when the challenge was issued for another booking key; when SHA-256 of `<nonce>:<solution>` does not start with `difficulty` zero bits; or when an earlier create presented the same nonce with a valid signature in the last 30 minutes. A repeat of the same `Idempotency-Key` is a replay (C44), not a reuse. Each of these answers is byte-identical to the answer to any other malformed body, so a caller cannot tell which layer refused. A correctly solved challenge between 3 seconds and 30 minutes old books. With `PUBLIC_CAPTCHA` unset, `captchaToken` is ignored and the config's `captcha` is null. With it set to `turnstile` or `hcaptcha`, the config names the provider and the site key, the widget page's policy adds that vendor's hosts, and a create without a token the vendor verifies fails with `invalid_request`. The difficulty is an instance setting, measured before stage 3 (ADR-0017, Q7).

## C46. Per-contact caps and what they reveal

`maxOpenBookingsPerContact` counts the contact's future `booked` reservations in the venue whose `bookedVia` is `widget`, by the normalized contact of REQ-G2. A public create that would exceed it fails with `online_booking_limit` (409) and writes nothing, and the booking that reaches the cap passes. Cancelled, seated, attended, no-show and past bookings do not count. Neither does a booking staff made for the same contact, nor a booking in another venue. An email that differs only in case or surrounding whitespace is the same contact. Null turns the cap off. Concurrent public creates by one contact never exceed it. The venue's `maxActivePerGuestPerDay` applies to a public create and fails with `guest_booking_limit`, as C35 says, and it is checked first when both caps are reached. A staff create is never refused by `maxOpenBookingsPerContact`. Both codes tell a caller who types a contact that it holds bookings in the venue. The contract accepts that (ADR-0017, Q9), bounded by `public_booking`. Availability takes no contact and answers alike for every contact, and the resend route answers alike whether a booking matches or not (C51).

## C47. Self-service token

A token is `<linkId>.<secret>`: a lower-case UUID, a dot, and 43 base64url characters from 32 random bytes. No two links share a link id or a secret. The database stores, for a link, the link id, the venue, the reservation, the SHA-256 hex hash of the secret, and the creation, expiry and revocation times. A scan of every table, and of the API's log output, after a create, a read, a modify, a cancel, a reissue and failed lookups finds neither a token nor a secret. A reservation has at most one link that is not revoked. The token is read only from `X-Self-Service-Token`. It names exactly one reservation: a read returns that booking, a modify or cancel changes only it, and no public route takes a reservation id or a venue id, so no token reaches another booking or another venue. A missing header, a malformed token, an unknown link id, a known link id with a wrong secret, an expired link, a revoked link, and a link of an erased booking all give `404` with `self_service_link_invalid`, byte-identical bodies and the same headers, on read, modify and cancel. The one exception is the cancel replay of C50. The lookup goes by link id and compares hashes with a constant-time compare, and an unknown link id runs the same compare against a dummy hash, which a test pins by counting the compares. A link expires 48 hours after the booking ends, its start plus its turn time, by the database clock: a read just before that instant works and one just after fails. Every self-service answer, a failure included, sends `Cache-Control: no-store`. Retention deletes a link row 30 days after it expires.

## C48. Self-service read and the guest view

`GET /v1/public/self-service` with a working token returns the guest view: the venue's name, locale, theme, public phone and public address (C64), the date, the local time, the party size, the status, the current version, the guest's name, the masked contact, the note, the stored consent, `changeableUntil`, which is the start minus `selfServiceCutoffMinutes`, and `linkExpiresAt`. The email `ana.garcia@example.com` reads `a***@example.com`, and the phone `+34600123456` reads `***56`. The view holds no reservation id, guest id, table, zone, service, duration, `bookedVia`, `ownerPrincipal`, `basis`, rating, reconfirmation, version history, or anything of another booking. The create, modify and cancel answers use the same view. A read changes nothing, emits no event and does not rotate the link. Reading works in every status until the link expires or is revoked: after a staff modify it shows the new party size and version, after a staff cancel it shows `cancelled`, and after the start it still answers.

## C49. Guest modify

`POST /v1/public/self-service/modify` with a working token, a UUID key and `{ version, ... }` changes only `partySize`, `commentary` and `guest.consent`. A body that names `date`, `time`, `tables`, `zone`, `rating` or `reconfirmation`, or that has no field besides `version`, fails with `invalid_request`. A change bumps the version by one, emits one `modified` event, keeps the attribution, and does not rotate the link, so the same token works after it. Setting the stored values changes nothing and emits nothing. The checks run in this order, and a request that fails several gets the first: a malformed body or key (`invalid_request`); the token (`self_service_link_invalid`); a repeat of the key, which returns the first result even after the cutoff or a later change; a booking that is not `booked` or that starts within `selfServiceCutoffMinutes` (`self_service_closed`); a `version` that is not the stored one (`reservation_changed`, nothing written); then the party rules. A guest who read version 1, after staff change the party and the version becomes 2, gets `reservation_changed`, and succeeds after reading again and sending version 2. With a cutoff of 120 minutes, a modify 121 minutes before the start passes and one 119 minutes before fails with `self_service_closed`. A cutoff of 0 allows it until the start. A `seated`, `attended`, `no_show` or `cancelled` booking fails with `self_service_closed`. A new party size runs the table search of a staff modify. It holds the new tables, or fails with `no_suitable_table` and keeps the old ones, never uses the overbooking ceiling, and is held to the narrower of the online and service party limits (`party_size_too_small`, `party_size_too_large`). With email on, a party size change sends one `confirmation` for the new version, with no link, within the limit of C61, and a note or consent change sends none, as C4 says. Staff writes are unchanged: they carry no version and never get `reservation_changed`.

## C50. Guest cancel and revocation

`POST /v1/public/self-service/cancel` with a working token and a UUID key cancels through the staff cancel: status `cancelled`, tables freed, version plus one, one `cancelled` event. In the same transaction it revokes the link and mints none. It returns the cancelled guest view with no token. With email on, the guest gets a `cancellation` with no link and the venue a `notice`. After it, a read, a modify, and a cancel with another key, all with that token, fail with `self_service_link_invalid`. A repeat of the same cancel, with the same key and the same token, returns `200` with the same cancelled guest view and version, writes nothing, emits no event and sends no email. That replay works until the link would have expired. After that, and after an erasure, it fails with `self_service_link_invalid` too. A cancel within the cutoff, or of a booking that is not `booked`, fails with `self_service_closed` and changes nothing. A staff cancel does not revoke the link: the guest still reads the cancelled booking until the link expires, and a guest modify or cancel gets `self_service_closed`. A guest who books again after a cancel gets a new reservation with its own token. A cancel that fails after any step leaves the booking and its link unchanged.

## C51. Link rotation: replay, staff reissue and resend

A link rotates in three ways, a repeat of the public create (C44), a staff reissue and a resend, and each revokes the old link and mints the new one in one transaction, so a reservation never has two working links. `POST /v1/venues/{venueId}/reservations/{reservationId}/self-service-link` with the `write` or `admin` role and an `Idempotency-Key` returns a new token once with its `linkExpiresAt`, with `Cache-Control: no-store`. The old token then fails with `self_service_link_invalid` and the new one works. A repeat of the same key rotates again and returns another token. A `read` role fails with `forbidden`, a reservation of another venue with `reservation_not_found`, and a reservation that is not `booked` with `invalid_transition`, each with the link unchanged. A reissue does not change the reservation's version and emits no event. It also works for a `booked` reservation that staff made, which then gets its first link. With email on and an email contact, each rotation sends one `self_service_link` email for the new link id. `POST /v1/public/{bookingKey}/self-service/resend` with `{ email }` answers `202` with the same body and headers whether the email matches no booking, one or several, and whether email is on or off. With email on, each future `booked` booking of that venue whose contact normalizes to that email gets a new link, sent to the address stored on the booking. With email off it changes nothing. The answer is sent before the address is looked up. The resend sends at most one email per address and venue every 15 minutes, includes a reservation in at most 3 resend emails ever, and names at most 5 bookings in one email, the earliest first. A booking it leaves out keeps its link, so a resend never rotates a link it does not send. Concurrent resends for one address send one email. A cancelled, erased or past booking gets nothing, and its link is unchanged. The email holds dates, times, party sizes and links on the widget origin (`/r?lang=<locale>#<token>`), and no guest name or note. Its text is in the stored `guestLocale` of the earliest booking it names, the booking whose stored address it goes to, and each link's `lang` is its own booking's stored `guestLocale`. A booking with no stored locale uses the venue's `locale`, and text with no shipped catalog falls back as C67 says. The request's own language, its `Accept-Language` included, changes neither the text nor any link: two bookings for one address booked in `en` and `fr`, the `en` one earlier, get one email whose text follows `en` (C67) and whose links carry `lang=en` and `lang=fr`, whatever the venue's locale or the request's headers. No token reaches a log, an event or the record of sent email. A body without one email address fails with `invalid_request`. The config answer's `linkResend` is true only when the resend can send: email on, a way to send it, and a widget origin. A read, a guest modify, a staff modify and a staff status change never rotate a link.

## C52. Rate limits on the public routes

This extends C28 with five rules, each with its own budget and setting in the C28 format. `public_read` matches every `GET` under `/v1/public/`, by client address, 300 per 15 minutes by default (`RATE_LIMIT_PUBLIC_READ`). `public_booking` matches `POST /v1/public/{bookingKey}/reservations` and `POST /v1/public/{bookingKey}/self-service/resend`, by client address, 10 per hour (`RATE_LIMIT_PUBLIC_BOOKING`). `public_venue` matches the same two routes, keyed by the booking key in the path, 100 per hour (`RATE_LIMIT_PUBLIC_VENUE`). `self_service` matches every request under `/v1/public/self-service`, by client address, 60 per 15 minutes (`RATE_LIMIT_PUBLIC_SELF_SERVICE`). `public_days` matches `GET /v1/public/{bookingKey}/days` (C63), by client address, 60 per 15 minutes (`RATE_LIMIT_PUBLIC_DAYS`), and that request also counts on `public_read` ([ADR-0021](../adr/0021-widget-day-status-zones-waitlist.md)). A request that matches two rules, a create (`public_booking` and `public_venue`), a self-service read (`public_read` and `self_service`) or a days read (`public_read` and `public_days`), counts on both, and when either is spent it is refused and neither is charged. A refusal is `429` with `rate_limited` and `Retry-After`, the same body whatever key, token or body the request carries, and it does no work: no booking, no rotation, no email. When many addresses spend `public_venue` for one venue, public creates for that venue are refused, and other venues, staff creates and that venue's public reads are not. A create that answers `400` or `404`, a malformed body, a failed challenge or an unknown booking key, gives back its `public_venue` charge and keeps its `public_booking` charge, so it never spends a venue's budget. Repeated and trailing slashes are matched like the plain path, and the limiter never reads the body. A request body over 16 KB under `/v1/public/` fails with `invalid_request` and `Cache-Control: no-store`, and the API stops reading it at the limit. `GET /w/{bookingKey}`, `GET /v1/venues/{venueId}/public.jsonld` and the staff `/v1` routes are not limited by these rules. `TRUST_PROXY` and `RATE_LIMIT=off` work as in C28, and an invalid setting stops the API at startup.

## C53. Erasure and retention end links

Erasure by guest id or by principal, and retention of a reservation, revoke and delete the self-service link of each reservation they blank, in the same transaction. Afterwards the token fails with `self_service_link_invalid`, the cancel replay of C50 included, and no link row remains for those reservations. Erasure by principal `widget` erases every online booking of the venue and ends all their links. The erasure counts of C5 do not change. A link of a reservation the erasure does not reach keeps working. A guest cancel is not an erasure: the cancelled reservation keeps its data for the venue's retention period. No public route erases data.

## C54. Guest blocklist on the public create

The public create calls the same create as staff, so the guest blocklist of [ADR-0018](../adr/0018-guest-blocklist.md) applies with no extra check, at the same point and with the same answer. For a contact on the venue's list, a public create at a time that would otherwise book fails with `booking_declined` and leaves no reservation, guest record, idempotency key, event, link or email, and the same key books after an admin removes the entry. At a closed or full time, the blocked contact gets the same code as anyone else. Public availability does not change for a blocked contact, and a contact blocked in another venue books. This case can pass only once ADR-0018 is built, which adds `booking_declined` to `errors.md`.

## C55. Guest data on the public channel

The public channel takes a name, one contact, the party size, the date and time, an optional note of up to 500 characters, consent only when the venue asks, and an optional language code (`locale`, one of the seven widget locales, C43). The language code is not contact data and holds no free text, and erasure and retention reset it (C5, C18). It has no allergy, diet, occasion, birthday, address or marketing field, and the contract says the note is not for health data. With `askConsent` off, a create or modify that sends `guest.consent` records nothing for it: the booking reads `unknown` with no `consentRecordedAt`, and a modify whose only change is that consent changes nothing. With it on, `granted` records `granted` with a time, and an absent value or `unknown` leaves `unknown`. Through the link a guest sets `granted` or `unknown`. `denied` fails with `invalid_request` whatever the setting, because the public channel never records a refusal. The public routes return the guest's own contact only masked (C48) and never another guest's data. Feed and webhook events for public writes carry ids, a type and a version only, as for staff writes.

## C56. Guest blocklist management

A venue `admin` with a staff session manages the venue's guest blocklist through `/v1/venues/{venueId}/blocklist`: add, list, `lookup`, and delete by id. A `read` or `write` session, and a key of any role, an `admin` key included, fail with `forbidden` on all four and change nothing. A request with no credentials fails with `unauthorized`, and a caller outside the venue fails with `venue_not_found`. An add takes `guestId` or `contact` in the body, exactly one, and an optional `reason` of `no_show`, `late_cancellation`, `conduct`, or `other`. A `contact` is normalized as a booking contact is, with the venue's default country, and stored only as a keyed hash. A contact that does not normalize, a reason outside the codes, both fields or neither fail with `invalid_request` and add nothing. A `guestId` adds one entry per email and phone of that guest and of every guest merged into it, and the response carries `bookedReservations`, the count of those guests' reservations still `booked`. A guest of another venue, a guest merged into another, and an unknown guest fail with `guest_not_found`. Two spellings of one contact are one entry. An add of an entry that exists returns it with `created: false` and its original reason, and writes no audit row. Each entry shows `id`, `kind`, `reason`, `createdBy`, the admin's account id, `createdAt`, `expiresAt`, which is `createdAt` plus the venue's `retentionDays`, and `active`, false when the entry was made under a key that is no longer configured. The list is newest first, with `limit` from 1 to 200, default 50, and following `nextCursor` visits every entry once, ties on `createdAt` included. A bad `limit`, a malformed cursor, and a cursor from another venue fail with `invalid_request`. A lookup by `guestId` or `contact` returns the matching entries of this venue only, or none. A delete returns the entry it removed, and an unknown id and an entry of another venue fail with `blocklist_entry_not_found`, the same answer, so a second delete fails with it too. A venue holds at most 10,000 entries. An add that would pass the limit fails with `blocklist_limit_reached` and adds nothing, an add of an entry that exists still succeeds at the limit, and of concurrent adds for the last place exactly one succeeds. Each entry created writes one `guest_blocked` row to the membership audit log and each delete one `guest_unblocked` row, in the same transaction, with the admin as actor and `blocklistEntryId`, and no contact, hash, guest id, or reason. No stored entry holds a clear contact. No response, the add, list, lookup, delete, and audit read included, holds a contact or a hash, the contact the caller sent included. A contact is never accepted in a URL: these routes fail with `invalid_request` on any query parameter other than `limit` and `cursor` on the list. Entries, cursors, lookups, and deletes of one venue never touch another. No MCP tool reaches these routes.

## C57. Guest blocklist on create, erasure and retention

A create whose contact matches an entry of the venue's guest blocklist (C56), under the current key or the previous one during a rotation, fails with `booking_declined` (409, not retryable). The body is `{ code, message, retryable }` and nothing else. Any spelling of the contact that normalizes to the same email or phone is refused. A staff session is refused like a key, an admin's included. The check runs last, after the per-guest cap and the table search or overbooking room: a blocked contact at a closed time, on a blocked date, at its daily cap, with no table free, with a named table already taken, or with a party too large gets the same code as any other contact, and gets `booking_declined` only where the booking would otherwise be made, overbooking room included. A declined create leaves no reservation, table allocation, guest record, guest audit row, idempotency key, event or email, so the same `Idempotency-Key` books once an admin removes the entry. A repeat of a create that succeeded before the entry was added returns the same booking, and adding an entry never changes or cancels an existing booking. A walk-in and a seat from the waitlist are never refused, and adding to the waitlist is not checked. A create with no contact, or with one that does not normalize, is not checked. An entry of another venue never refuses a create, even one stored with this venue's hash. A create racing an add either books or is declined, never both, and once the add returns, a new create for that contact is declined. Availability and the explanation never read the list: they answer the same with the list present or absent, so a blocked contact can get `booking_declined` at a time they show as free, as C35 allows for the cap. Erasure by guest id, by contact or by principal deletes no blocklist entry, and its response adds `blocklistEntriesKept`, the number of the venue's entries that match the email or phone of a guest record it deleted, merged guests included, or the contact it was given. Entries of another venue are not counted. A repeat of an erasure by guest id deletes nothing and reports 0. Retention deletes an entry on its first run after the entry's `expiresAt`, which is `createdAt` plus the venue's `retentionDays`, in bounded batches, and writes no audit row. Younger entries stay, each venue uses its own period, other venues are untouched, and overlapping runs delete each entry once.

## C58. Idempotency key on every reservation and waitlist write

Create, walk-in, modify, cancel and status of a reservation, and add, seat and cancel of a waitlist entry, each sent twice with the same `Idempotency-Key`, return the same status and body both times and write once: one reservation, one event, one waitlist entry, one seat, one cancel. Sent concurrently with one key, every call gets the same success and the write happens once, with no `500` and no conflict for the duplicates. Keys are scoped to the venue: the same key in two venues writes in each, and never returns the other venue's data. A key used for another kind of write, a cancel of another waitlist entry, or a seat of another entry fails with `invalid_request` and writes nothing. A repeat of a waitlist add key with a different body returns the first result and adds nothing, as a repeated create does. A write that fails stores no key: a cancel of an unknown entry, a seat with no free table or a create refused with `slot_taken` leaves the key free, and the same key succeeds once the cause is gone. The reservation routes and the waitlist seat require the header. The waitlist add and cancel accept it, and without it they behave as before, so two adds make two entries. A cancel of a booking that erasure blanked and left booked succeeds, frees its tables and keeps its one tombstone, and never answers `500`. `PUT /config` and erasure take no key. Every MCP write tool that maps to one of these routes takes an optional `idempotencyKey` and sends it unchanged on every call, generates a new key per call when it is omitted, and says in its description to resend the same key on a retry.

## C59. A waitlist entry is seated once

Seat requests for one waitlist entry sent concurrently with different `Idempotency-Key` values seat it once: exactly one request succeeds with the walk-in reservation, and every other request fails with `invalid_transition` (409) and writes nothing, so the venue holds one reservation for the entry. The status of the entry and the walk-in booking change together or not at all, so a seat that fails, for example with `slot_taken`, leaves the entry `waiting`. Concurrent seats with one key still all return the one reservation (C58). A seat whose key already belongs to another write, such as an unrelated create, fails with `invalid_request`, leaves the entry `waiting` and writes no event. A seat of an entry that is already `seated` or `cancelled` fails with `invalid_transition`, and a seat racing a cancel of the same entry ends with the entry either seated or cancelled, never both.

## C60. Guest fields on the MCP write tools

`reservation.create`, `reservation.walk_in` and `waitlist.add` take the guest as flat `guestName` and `guestContact` or as a `guest` object with `name` and `contact`, and both forms send the same guest to the engine. `reservation.create`, `reservation.walk_in` and `reservation.modify` take `consent` flat or as `guest.consent`. A field given in both forms with different values fails the call and writes nothing. `reservation.create`, `reservation.walk_in`, `reservation.modify` and `waitlist.add` reject an argument they do not list, and a key of `guest` they do not list, with an error that names it, and make no request to the engine, so a call can never create a booking or entry with no guest because of the shape of its arguments. `idempotencyKey` stays optional on all of them.

## C61. Public channel limits on dates, email, retention and framing

These rules close abuse found in a security review of the public channel (ADR-0017, amendment of 2026-11-17).

The public channel's effective horizon is the smaller of the online `maxAdvanceDays` and the venue's. When both are null it is 365 days, and the config answer shows `maxAdvanceDays` 365. A public create for today plus 365 days, in the venue's time zone, books, and one for a day later fails with `beyond_booking_horizon`, as availability leaves it out. A value either setting holds wins over the default, a looser one included: an online horizon of 500 books 400 days ahead, and a venue horizon of 10 refuses 11 days ahead whatever the online one says. Staff creates keep their own rules.

A date that is not a real `YYYY-MM-DD` calendar date, or is earlier than `1900-01-01` or later than `9998-12-31`, fails with `invalid_request` on the staff create and walk-in, the public create and availability, and the staff availability, explanation, agenda, pacing and floor. A staff create or walk-in whose time is not `HH:MM`, and a floor query with such a time, fail the same way. No route answers `500` for a date: `9999-12-31`, `0001-01-01`, `2030-02-30` and `abc` get a `400` everywhere.

A guest's `lastVisitAt` is never later than now. A booking made for a future date counts from the moment it was made, so a booking a stranger makes with a guest's contact, and then cancels, does not keep that guest from retention: when the guest's other visits are older than the period, the next run expires the guest and blanks the cancelled booking with them. A booking that is not cancelled still keeps its guest until it ends plus the period (C18).

With email on, a guest's own party change sends at most 3 `confirmation` emails per reservation over its life, each at least 15 minutes after the previous one. A guest who changes the party ten times in a row gets one email for the changes, and every modify still answers `200` with the new version, so the answer does not show whether an email went out. A modify that changes nothing sends nothing. The booking's first `confirmation`, the `cancellation` and the venue's `notice` are not counted, and no email a staff change sends is held back, though a staff party change's `confirmation` counts toward the 3. The emails to the guest, `confirmation` and `cancellation`, carry no guest name, since whoever books types it. The venue's `notice` still shows it.

A public repeat of the create key of a booking that erasure or retention blanked fails with `invalid_request`, byte-identical to a malformed body, mints no link, writes nothing, and shows nothing of the booking. A staff reissue for an erased booking fails with `invalid_transition` and mints no link.

An `allowedOrigins` entry is accepted only when it equals, in lower case, the origin of the URL it names, with a host of letters, digits, hyphens and dots. `https://a.example;`, `https://a.example,https://b.example`, `https://a'b.example`, `https://a.example:443`, `https://a.example/`, `https://a_b.example` and a port above 65535 fail with `invalid_request`. `https://Shop.Example:8443` reads back as `https://shop.example:8443`. The widget page's `frame-ancestors` leaves out any stored entry that does not pass this check, so a value saved before it was enforced never reaches the header, and a list with no valid entry gives `'none'`.

## C62. The public channel never takes a start in the past

`GET /v1/public/{bookingKey}/availability` never lists a time whose start is earlier than now plus the effective lead time (the larger of the venue's and the online one, 0 by default), in the venue's time zone. A start exactly now is listed. A date before today returns `200` with `times: []` and `reason: "past_date"`, not an error. A date past the online horizon returns `times: []` and `reason: "beyond_horizon"`. Any other empty answer, and any non-empty one, has `reason: null`. `POST /v1/public/{bookingKey}/reservations` for a start earlier than now fails with `lead_time_violation` and writes nothing, for a past date, for an earlier time today, and with the lead time at 0. A time inside a positive lead time fails with the same code. The check runs in the create path the public and the staff channel share, before the booking transaction, and the exclusion constraint still decides overlap, so two parallel public creates for one free slot still give one booking and one `slot_taken`. The staff create, the staff availability and the walk-in are unchanged: staff can still book a past date or time. A guest's self-service modify cannot move the date or time (C49) and is closed once the booking starts, so it cannot place a booking in the past. The guest view carries `maxPartySize`, the venue's online party maximum, so the guest's change screen can stop there.

## C63. Public day status

This case specifies the day status of [ADR-0021](../adr/0021-widget-day-status-zones-waitlist.md), section 1.

`GET /v1/public/{bookingKey}/days?from=&days=&partySize=` returns `{ from, partySize, days }`, with one entry `{ date, status, firstTime }` per date from `from`, ascending, each once, and nothing else. Over a grid of dates and party sizes inside the online limits, a date is `available` exactly when `GET /v1/public/{bookingKey}/availability` for that date and party lists a time, and its `firstTime` is then the first listed time. It is `outside_window` exactly when availability answers `past_date` or `beyond_horizon`. A date on which no online service opens, after the online `services` and `weekdays`, and a blocked date are `closed`. A date the venue serves online on which every start is already past or inside the lead time is `closed` too, so late evening today is `closed` and not `full`. A date the venue serves online with a start still open to the clock and no time for the party, for example with every fitting table held, is `full`: `full` is never the answer to the clock alone, only to tables, capacity or limits. The status is the first of `available`, `outside_window`, `closed` and `full` that applies, so a blocked date before today is `outside_window`. `firstTime` is null for every status but `available`. Without `from` the range starts today in the venue's time zone, and without `days` it holds 12 dates. `days` of 1 and of 14 give 1 and 14 entries. `days` of 0, 15, `1.5` or `abc`, a `from` that breaks the date rules of C61, and a `partySize` that is missing or not an integer of at least 1 fail with `invalid_request`. A `from` before today gives `outside_window` for each date before today and the normal status from today on, and a range that crosses the effective horizon of C61 gives `outside_window` from the first date past it. A party below the online minimum or above the online maximum fails with `invalid_request`, where C42 answers an empty list: the config already publishes the limits, and a range of `full` days would offer a waitlist the guest cannot join (ADR-0021). The route takes no contact, so the per-contact caps and the guest blocklist never change it, and a status is a snapshot that holds no table (C3). A scan of every answer, errors included, finds no table id, zone, service name, count of tables, covers or seats, or guest data, as C40 requires. An unknown, rotated, malformed or disabled key gives the `404` with `venue_not_found` of C40, with the same body and headers. Every answer, an error included, sends `Cache-Control: no-store`. It is limited by `public_read` and `public_days` (C52).

## C64. Public address and privacy notice URL

This case specifies the address and the notice link of [ADR-0021](../adr/0021-widget-day-status-zones-waitlist.md), section 5.

`PublicVenue.address`, in the config answer of `GET /v1/public/{bookingKey}` and in the guest view of C48, is null while the venue's `publicProfileEnabled` is off, whatever street, postal code and locality the profile holds, and null when the profile holds no street. With the profile on, it is one line made from the profile: `street`, then `postalCode` and `locality` joined by a space, separated by `, `, with a part that is not set left out, so `Calle Mayor 1`, `28013` and `Madrid` give `Calle Mayor 1, 28013 Madrid`. It holds no region, country or coordinates. Turning the profile off makes it null from the next request, and a profile change shows on the next request. The venue's `noticeAddress` never appears in any public answer, under any key, whatever its value. `GET /v1/venues/{venueId}/online-booking` reads `privacyNoticeUrl` null for a venue that never set it. A `PUT` with an `https` URL of at most 2048 characters stores it, and `GET` and the public config read it back as sent. `null` clears it, and a `PUT` without the field keeps it. Each of these fails with `invalid_request` and changes nothing: a URL that is not `https` (`http`, `javascript:`, `data:` or no scheme), one with no host, one that carries credentials (`https://user:pass@host/`), one that holds whitespace or a control character, one over 2048 characters, and a value that is not a string or null. A `read` or `write` key or session fails with `forbidden` and the value reads back unchanged, and a caller outside the venue fails with `venue_not_found`. The public config returns the stored value, or null, and nothing about it changes any other field. Two venues keep their own address and URL: venue A's key never returns B's. The C40 scan of every public answer still holds, with these two fields as its only documented additions.

## C65. Reservation trace

`GET /v1/venues/{venueId}/reservations/{reservationId}/trace` returns the reservation's events oldest first, each with `eventId`, `type`, `version`, `occurredAt` and the `Idempotency-Key` of the write that made it. A create, a modify and a cancel with three keys return three entries with versions 1, 2 and 3 and those keys, and an `erased` entry has a null key. A key stored for a self-service link never appears as the key of an event. A public booking shows the key the client sent, without the engine's internal prefix. Each entry also carries `channel`, `actor` and `recorded`, read from the origin stored on the event (ADR-0023), so a later modify or cancel shows its own origin and not the booking's. `channel` is `widget`, `staff`, `api` or `mcp`. An entry made with an API key that sent `X-OpenCovers-Channel: mcp` reads `mcp`, and that label is set by the key's holder, so it is a label and not proof. `actor` is null for `widget`, the member's display name for `staff` (only a member of this venue, and null when the name is missing, looks like an email or the user is no longer a member), and the key reference `key_` plus 12 hex characters for `api` and `mcp`. `actor` is never an email, a user id or a guest value. An entry made through the public channel shows the key the client sent, without the engine's prefix, whoever made the booking. An event stored without an origin (a row from before ADR-0023, or a retention sweep) has `recorded` false and `actor` null: a `created` entry then takes `channel` from the booking's `bookedVia` as before, and any other entry has `channel` null (unknown). `recorded` is true when the origin was stored. The answer has only `reservationId` and `entries`: the top-level `source` and `actor` (the booking's `bookedVia`, a staff email for a booking made from a session) were removed, a breaking change made while the project is pre-alpha (ADR-0023). No value anywhere in the answer is an email-like string, for a booking made from a session, with an API key or through the public channel. A key with the `read` role can read it. The answer holds no guest name or contact. A reservation id of another venue or an unknown id returns `reservation_not_found`, and the feed `reservation.events` is unchanged.

## C66. Public zones and service names

This case specifies the zones and the service names of [ADR-0021](../adr/0021-widget-day-status-zones-waitlist.md), section 2 and its "Times grouped by service".

`GET /v1/venues/{venueId}/online-booking` reads `publicZones` `[]` and `showServiceNames` false for a venue that never set them. `PUT` is admin only like the other settings: a `read` or `write` key or session fails with `forbidden` and both read back unchanged, and a caller outside the venue fails with `venue_not_found`. `publicZones` stores 2 to 10 distinct names, each the `zone` of at least one of the venue's tables at the time of the save, compared exactly, and reads back in the order sent. Each of these fails with `invalid_request` and changes nothing: a list of exactly one, more than 10, a duplicate, an empty name, a name that is no table's zone (another venue's zone included), `null`, and a value that is not an array of strings. `[]` clears it, a `PUT` without it keeps it and does not check it again, and `showServiceNames` takes `true` or `false` only. The effective public zones are the names of `publicZones` that are still the zone of at least one table, in its order; a renamed or deleted table can make a stored name drop out. With fewer than two effective public zones and `showServiceNames` off, the config, availability, `/days` and the create answer exactly as without these settings: the config's `zones` is `[]`, availability has no `slots`, and any `zone` on availability or the create fails with `invalid_request`. With two or more, the config's `zones` lists them in order. Availability then adds `slots`, one `{ time, zones }` per time of `times` in the same order, where `zones` lists, in order, the public zones in which a free table or combination fits the party at that time, and is `[]` when only a table outside them fits. With `showServiceNames` on, each slot also has `service`, the name of the service a public create at that time books under, and without public zones a slot is `{ time, service }`. With it off no answer names a service. `times` is always exactly the times of `slots`, and without `zone` it is the list of C42. The optional `zone` query accepts only a name in the config's `zones`, compared exactly, so never while there are fewer than two effective public zones; any other value, an empty one included, fails with `invalid_request`, the same body whether the value is another zone of the venue or no zone at all. With it, `times` and `slots` hold only the slots whose `zones` contain it, and over a grid of dates, times and party sizes a time is listed exactly when a public create with that `zone`, a contact that holds no booking and nothing else changing, succeeds. The public create takes `zone` under the same rule: any other value fails with `invalid_request` and writes nothing. With it the staff read shows a table in that zone and `zone` set to it, and when no free table or combination in that zone fits, the create fails with `slot_taken` and writes nothing, even when a table outside the zone is free and with any ceiling. No public error carries a count of the zone's tables or seats. Without `zone` the create uses every table, as before (ADR-0021, Q4). The guest self-service modify still refuses `zone` (C49). `/days` takes no `zone` in v1: a day is `available` when a create without `zone` could book, so a day shown `available` may have no time in the zone a guest picked, and availability with that `zone` is authoritative. The guest view (C48), in the create answer and through the link, does not show the zone in this stage. No public answer holds a table id, a count of tables, covers or seats, or a zone name other than an effective public zone, and the C40 scan holds with `zones`, `slots[].zones` and, while `showServiceNames` is on, `slots[].service` as its only additions. Two venues keep their own settings: venue A's key never returns B's zones. The guest sees the zone names as stored; a public label per zone and locale is a possible later addition.

## C67. Email language

This case specifies the guest's language in emails of [ADR-0024](../adr/0024-guest-email-language.md).

An email to the guest about a reservation is written in its resolved locale: the reservation's stored `guestLocale` (C43) when an email catalog ships for it, otherwise the venue's online-booking `locale` when a catalog ships for that, otherwise `es`. This holds for every guest email kind: `confirmation`, at create and after a change (C4, C49), `cancellation`, by staff or by the guest (C50), `self_service_link`, on a create replay and a staff reissue (C44, C51), and `self_service_link_resend`, whose text follows the earliest booking it names (C51). With `en` shipped, a public create with `locale` `en` in a venue whose `locale` is `es` gets its `confirmation` and later `cancellation` from the `en` catalog, and a booking with `guestLocale` null in a venue whose `locale` is `en` gets them from the `en` catalog. A booking made by staff, an API key or MCP has `guestLocale` null and gets the venue's language. The venue's `notice` is always in the venue's online-booking `locale`, then `es`, never the guest's, whatever `guestLocale` holds. A stored or venue locale with no shipped catalog falls through the chain to the next step: no email fails, throws or goes unsent for a missing catalog, and a booking stored with a locale that has no catalog gets the venue's language, or `es`. The date in an email is the reservation's calendar date formatted for the resolved locale, never shifted by a time zone, and the time stays the venue's local time. Every `/r` link in a guest email carries `lang=` the booking's stored `guestLocale`, or the venue's `locale` when it is null, whether or not an email catalog ships for that locale. The language never changes what is sent otherwise: no guest name in guest emails (C61), no note or other typed text, the same once per reservation, kind and version rule, the same guest modify limit (C61), and no email while `notificationsEnabled` is off. A guest modify, a staff modify, a replay of the create key and the resend request never change `guestLocale`, so the next email follows the language stored at create. Erasure and retention reset `guestLocale` to null (C5, C18), so a later email about that booking, if any, is in the venue's language.

Every shipped email catalog has exactly the message ids of `es` and, for each id, the same `{slot}` names, and the shipped locales always include `es` and are a subset of the seven widget locales. Only reviewed catalogs ship (ADR-0024, Q3): the case does not require all seven, only parity over those that ship, and a locale among the seven without a shipped catalog is served by the fallback above. The waitlist join email of ADR-0021 follows the join's `locale` under the same chain once that route is specified.
